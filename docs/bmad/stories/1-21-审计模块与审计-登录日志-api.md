## Intent

**Problem:** 1.16–1.20 把所有写操作的审计都留成了过渡实现：`/admin/*`、`/auth/api-tokens*`、租户写操作只写结构化日志（`audit_logs_written=false`），自助 operation（登录、登出、改密、TOTP、再认证、撤销会话）完全绕过审计钩子，`cancelTask` 因审计钩子 fail-closed 在隔离矩阵里是 `FailClosed`，acting-as 只有上下文没有落库；没有审计/登录日志的读取 API；没有任何检查能发现「写 operation 缺 Audit 声明」或「声明了 Audit 却没有记录」；`audit_logs` 的分区滚动没有在真实审计写入下联调过。

**Approach:** ① 审计模块 `internal/platform/audit`（architecture §5：`audit` 属 platform）：`Recorder.Record(ctx, Action, Event)` 在**业务事务内**写 `audit_logs`——审计写入失败 = 事务整体回滚 = 500 可重试（IMP-19，fail-closed），`Record` 拒绝事务外调用；操作者/acting_as/request_id/来源 IP/User-Agent/租户取自请求上下文，变更摘要写入前经 `pkg/redact`；② 真实审计钩子 `Writer.Auditor()` 替换 `adminAuditor`/`DenyAuditor` 默认（运行期兜底：声明了审计的成功请求却无审计行 → Error 日志 + 计数；未登记目录的 `x-audit` operation 在 Begin 即 500）；`WithSelfService` 不再绕过审计钩子；③ 27 个 `x-audit: true` operation 的写路径逐个改造（各在既有事务里 +1 个 `Record` 调用）；④ 读取：`GET /audit-logs`、`GET /audit-logs/{auditId}`（租户主体仅见自己租户且字段裁剪；平台不带 `X-Tenant-ID` 跨租户、带则代租户）与 `GET /admin/login-logs`（平台全局）；⑤ `make audit-check`（并入 `contract-check`）：静态门禁 `gates audit` + 真实路由集合检查，均带负向样本；⑥ 隔离矩阵扩充（`cancelTask` 转 `Driven`、新增 audit-logs 驱动）；⑦ 真实联调：不可篡改（真实 app 账号 UPDATE/DELETE 被拒）、同事务回滚（真实 MySQL 注入审计写入失败）、`partition.maintain`（真实 lingedge_maint）、Request ID 追踪。

## 关键实现点

- **事务方案（AC6/IMP-19，写入 ADR-018 修订记录）**：评估三种方案——A「HTTP 中间件包事务、请求结束统一写审计」会把登录失败计数/节流/`login_logs` 等本应独立提交的写入卷进同一事务，也无法表达「登录成功写会话 + 审计、失败只写日志」；B「事务外尽力而为」违反 IMP-19；C「Service 在业务事务内显式 `Record`」——侵入最小（1.12/1.16–1.20 的写路径本来就各有 `withTx`，每处只加一个调用，事务结构不变）且可被门禁强制。选 C，并用三道防线使它不可绕过：`Record` 不在事务内 → `ErrNotInTx`；`Record` 的动作必须在 `audit.Catalog` 且与请求 operation 登记的动作一致；`gates audit` 要求每个目录动作都有 `.Record(ctx, audit.ActionX, …)` 调用。
- **fail-closed**：审计 INSERT 失败 → `Record` 返回错误 → 服务返回错误 → 事务回滚 → `apierr.Internal`（500 `internal.error`，响应不含内部原因）。测试用 root 建 `BEFORE INSERT` 触发器在真实 MySQL 上注入「写入某动作的审计行时报错」（无 Mock，真实应用账号的 INSERT 真的失败）。
- **审计内容（AC1）**：操作者（`actor_type` user/api_token、`actor_user_id`、`actor_token_id`、`actor_label` 邮箱/令牌前缀、`actor_tenant_id`）、被操作对象所属租户 `tenant_id`（事件显式给出 > 租户范围 Scope > 空）、`acting_as`（`httpx.ActingAsFrom` 或 Scope 标记）、对象类型/uid、动作、结果、脱敏的变更摘要、`request_id`、来源 IP（`httpx.ClientIPFrom`，4/16 字节）、User-Agent。变更摘要只含「改了什么」的字段名与非敏感取值（邮箱、角色码、令牌前缀、配额键值、settings 只记键名）；`pkg/redact` 兜底（敏感键 → `***`），超 16 KiB 整体替换为 `{"truncated":true}`。
- **自助 operation 与公开路由**：登录成功（`auth.login`，含 MFA 第二步 `verifyTotp`）、MFA 挑战发放（`auth.mfa_challenge`）、登出、改密、撤销会话、再认证、TOTP 启停都在各自既有事务里写审计，主体尚未进入上下文的登录显式给出 `Event.Actor`。会话与审计同事务：审计写不进去则不建立会话。
- **幂等**：幂等重放不重复写审计（只有真正执行的那次写一条）；幂等键下首次 500 后同键重试正常执行（测试覆盖 `createUser`）。
- **读取 API（AC4）**：`GET /audit-logs` 游标分页（`id` 倒序，cursor 为 `id:<n>` 的 base64url，非法 → 400），过滤 `action/resource_type/resource_uid/actor_uid/tenant_uid/result/request_id/from/to`；仓储层按 Scope 限定可见范围（租户范围强制 `tenant_id = ?`，调用方无法省略）。**字段裁剪**：租户可见响应中 `acting_as` 记录抹去平台操作者（`actor_label=platform`，无 `actor_uid/ip/user_agent`），`changes` 递归剔除 R-T1 内部标识键（`leakguard.ForbiddenKey` + `cluster*/node*` 前缀，与 taskapi 同一规则）。不属于自己租户/平台级/不存在 → 404 逐字节一致。`GET /admin/login-logs`：平台全局，过滤 `event/identifier/ip/from/to`，复用 `LoginLog` schema；`GET /auth/login-logs` 不变。
- **只 INSERT（AC2）**：仓储层只有 `Insert/List/Get`；`lingedge_app` 无 UPDATE/DELETE（迁移 000003）；API 没有写路由（对 `/audit-logs*` 的写方法 404）；测试用真实 app 账号尝试 UPDATE/DELETE/TRUNCATE/DROP/ALTER 全部 1142，root 被触发器拒绝。
- **分区（AC3）**：`partition.maintain`（1.15）不变；真实联调见测试。保留期 `DROP PARTITION` 属 3.48，**未实现**，已在 `docs/database/{README,platform-identity}.md` 标注。
- **门禁（AC1，写入 ADR-017 修订记录）**：`make audit-check`：① `gates audit`——openapi 写 operation 必须 `x-audit: true`（例外清单 `scripts/gates/data/audit-exempt.txt`：`checkDomainAccess`、`validateRule`、`parseCertificate`，各带理由；过期/缺理由/指向读 operation 或已声明审计的条目失败）、`audit.Catalog` ⇄ openapi（目录里的 operation 必须存在且 `x-audit: true`）、每个目录动作必须有 `.Record(ctx, audit.ActionX, …)` 调用（AST 扫描非测试源码；动作不是 `audit.Action*` 常量 → 「不可核对」失败）、动作常量与目录互相覆盖；② 真实路由集合检查 `TestAuditCoverage`（写 operation 缺 Audit、声明了 Audit 却未登记目录）。负向样本：`scripts/gates/audit_test.go`（13 个变异：写 operation 缺声明、例外过期/缺理由/指向已审计或读 operation、目录登记非审计或不存在的 operation、孤儿常量、删除唯一记录者、动作非常量、引用未声明常量、无法解析的文件、openapi 解析为空）与 `contracttest/auditcoverage_test.go`（写 operation 缺声明、声明未登记、空路由集）。

## 默认值与口径（[ASSUMPTION] 标注）

| 参数/口径 | 取值 | 说明 |
|---|---|---|
| 只记录成功的写操作 | 事务回滚的失败没有变更，也无审计行 | 访问日志与 `login_logs` 覆盖失败/拒绝；`result` 取值 `failure/denied` 保留给后续「被拒绝的安全事件」（遗留） `[ASSUMPTION]` |
| 租户可见时平台操作者的呈现 | `actor_label=platform`，无 `actor_uid/ip/user_agent` | platform-identity §3.1「acting_as 不泄漏平台内部字段」的具体裁剪口径 `[ASSUMPTION]` |
| 变更摘要上限 | 序列化后 16 KiB，超限整体替换为 `{"truncated":true}` | 工程取值；保证审计写入不因体积失败 |
| 游标 | `id:<n>` 的 base64url，`id` 倒序 | 与 `/auth/login-logs` 同一约定 |
| 幂等重放 | 不重复写审计 | 重放不执行操作 |
| 审计例外清单 | 3 项只读式 POST | 见门禁 |
| 幂等重放/`revokeApiToken` 已吊销 | 仍写一条审计（`changed=false`） | 避免「成功响应却无审计」的歧义 |

## 遗留与风险

- **失败/拒绝类审计（`result=failure|denied`）M1 未写**：被授权钩子拒绝（403）、校验失败（4xx）、登录失败的安全事件目前只在访问日志与 `login_logs`；需要「安全事件审计」的场景（如越权尝试、acting-as 被拒）另开 Story，并须解决写入放大/攻击面（认证用户可刷审计表）问题。
- **保留期清理（`DROP PARTITION`）未实现**：属 Story 3.48；之前 `audit_logs` 只增不减，365 天保留策略未生效。`pmax` 非空告警/`doctor` 检查随 1.42。
- **每个新的审计 operation 必须同步三处**：`audit.Catalog`、业务 Service 的 `Record` 调用、openapi `x-audit`——门禁会在缺任何一处时失败，但「Record 调用写在错误的事务/分支里」只能靠该 operation 的集成测试发现（运行期兜底只在 2xx 且零记录时报警，不校验记录内容）。
- **运行期兜底不阻断响应**：「声明了审计却没有记录」在响应已写出后才发现（Error 日志 + 计数），不能回滚；因此防线在 CI（目录 + AST 门禁 + 集成测试），而不是运行期。
- **审计记录的 tenant_id 取舍**：平台路由（如 `PATCH /tenants/{id}`）的审计 `tenant_id` 是目标租户（租户因此能在 `/audit-logs` 看到「平台改了我的租户」，操作者被裁剪为 `platform`）；平台级对象（`/admin/users|roles`）`tenant_id` 为空，租户不可见。
- **租户用户的 `actor_label` 是邮箱**：租户视角能看到本租户其他用户的邮箱（同租户内可见，合理）；若产品要求更严格需改为展示名。
- **`task_events` 无 `request_id` 列**：经 `task_id` 关联追踪，无缺口；若要「按 Request ID 直接检索事件」需追加迁移（本 Story 不需要）。
- **审计表写入延迟与体量**：每个写操作多一次 INSERT（同事务）；高频写操作（如未来的缓存刷新）接入审计时需评估体量与分区粒度（目前按月，365 天保留）。
- `tests/apistack` 的装配仍是 `cmd/lingedge-server` 装配的镜像（`TestRegisteredRoutesMatchServerBinary` 兜底路由集合）。

## 开发记录

### 设计取舍

- **审计属于 platform，不是新的业务模块**：architecture §5 把 `audit` 列在 `platform/` 下；`internal/platform/audit` 不依赖任何业务模块，业务模块依赖它（符合依赖方向）。认证主体经 `ActorProvider`（返回基本类型）接入，`domain` 包不 import 审计包；`ports` 清单不需要变更。
- **目录（Catalog）是唯一来源**：operation → 动作登记表既被运行时校验（记录的动作必须属于请求的 operation）、也被门禁（AST）读取；常量与目录互相覆盖，避免「新增动作忘了登记」或「登记了没人记录」。
- **运行期兜底 vs CI**：运行期只能报警不能回滚（响应已写出），所以强制力放在 CI；运行期兜底的价值是发现「CI 没覆盖到的分支」（某条成功路径漏了 Record）。
- **登录/MFA 挑战也记录**：口令正确但需要第二因子时发放挑战同样是安全相关状态变更；记录它也避免了 `login` 返回 200 却无审计行的兜底误报。
- **R-T1 裁剪复用既有规则**：`StripInternal` 与任务中心视图同一规则（`leakguard.ForbiddenKey` + `cluster*/node*` 前缀）；矩阵里断言器的 IP 字面量检查对审计 operation 关闭是有意的（`ip` 是租户自己用户的来源地址）。
