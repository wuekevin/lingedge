## Intent

**Problem:** 1.37 收尾时登记了本机可做的遗留：向导英文界面仍显示服务端固定中文消息；向导固定亮色；1.36 登记的两条对比度例外（light `chart-3` 2.93:1、Arco 暗色实心按钮 `#fff` 对 `#7C93FF` 2.81:1）；1.34/1.35 文档里「cmd/lingedge 尚未链接 manifest / 待 1.35」的过时表述；以及 1.24/1.35/1.37 报告里被推迟的若干项。用户要求：本机可做的必须做完再进下一个 Story，功能代码写全，只有「需真实环境」「属后续 Story」才登记。

**Approach:** 逐项核对遗留并判定（见末尾「逐项处置表」）。本机可做项全部实现并带正/负向测试；没有新增迁移、没有改 OpenAPI/proto（契约冻结点不动）、没有新增依赖。

## 做了什么

### 1. 向导服务端消息 i18n

- **映射依据是稳定标识，不是文案**：错误码 `error.code`、环境检查项 `items[].key`、步骤 `step`。服务端文案语言固定（检查项/成功回执为中文，错误 `message`/`details[].reason` 多为英文），OpenAPI 形状与语义不变。
- `frontend/setup/src/api/servermsg.ts`（句式表）+ `useServerText.ts`（渲染）：
  - 错误说明 `errors.code.<code>`（zh-CN/en）；**未知错误码回落到服务端 `message`**（标注其语言、`data-localized="false"`），错误码与 Request ID 的展示不变。新增 `SetupApiError.serverMessage` 保留原文。
  - 环境检查项（15 条文案）、步骤成功回执（database/redis/init_db/system/keys/complete，含多片段拼成的 complete 与 database）、`details[].reason`（约 45 个固定句式，含口令策略与 TOTP 引导）按固定句式取出动态值（时间、路径、版本、数量、指纹……）后走 `serverMsg.*` 词条；对不上的整体回落原文，不丢信息。
  - 界面：`SetupError` 新增说明行；`EnvStep`/`ResultNote`/`CompleteStep` 的服务端文案、逐字段原因（`DatabaseStep/RedisStep/AdminStep/SystemStep`）均经映射。
- **对账（缺键 CI 失败）**：`pnpm run check:setup-codes`（已并入 `frontend-lint` 与 `check`）从 **Go 源码与 OpenAPI 自动推导**：`internal/platform/setup` 与 auth 引导路径里引用的 `apierr` 码（含 `Validation/NotFound/Internal/Conflict` 隐含的码）、`codes.go` 里全部 `setup.*` 码、OpenAPI `/public/setup/*` 声明的错误响应码、前端自有 `client.*` 码（共 16 个）；`steps_db.go` 的全部 `add("key", …)` 检查项（8 个）；产生回执的步骤。要求 zh-CN 与 en 词条齐全、`servermsg.ts` 句式表覆盖、句式引用的词条 id 存在。`scripts/setup-codes.test.mjs` 有 5 个负向自测（删词条、`codes.go` 新增 `setup.*`、setup 包引用新业务码、新增检查项、句式 id 缺词条）。
- **句式不会悄悄漂移**：`servermsg.test.ts` 的样本直接从 Go 源码抽取（15 条检查项文案、全部静态 `Reason`），服务端改了句式而前端没跟上，测试失败；真实 server 的 E2E 在英文界面断言「零回落、零中文」（`expectNoUnlocalized`，每个对比度检查点都执行）——它在本 Story 开发中**真实抓到过一次漂移**（complete 回执末尾的迁移口令说明段），已补句式。

### 2. 向导暗色主题

- `setup/src/theme.ts`：偏好 `auto|light|dark`（同标签页 `sessionStorage` 保留，非敏感）；`auto` 跟随系统 `prefers-color-scheme` 且**实时跟随系统切换**；经 shared 的 `applyTheme` 写 `<html data-theme>`（颜色全部来自 shared 令牌，组件里没有主题分支，`app.css` 去掉固定的 `color-scheme: light`）。顶栏新增「主题」选择；`main.ts` 在挂载前先应用，避免暗色系统下首帧闪亮色。
- 审计：E2E 对比度审计器扩展——**解析渐变色标**（品牌侧栏；`color-mix` 产生的半透明色标先叠到页面底色上，文字对每个色标都 ≥4.5:1，取最坏值），并有负向自测；`expectTheme` 断言主题属性与页面底色确实随主题变化。新增 Go 场景 `TestBrowserWizardFullDarkEnglish`（Chromium `colorScheme: dark`，TCP + TOTP + 英文，全 8 步每页审计）；`TestBrowserWizardBadToken` 改为暗色 + 英文；`TestBrowserWizardNonEmptyDatabase` 改为英文。截图已人工核对（环境检查、TOTP、完成页）。

### 3. 1.36 登记的对比度例外（UD-14 提议令牌范围内）

- **light `chart-3`**：`#D9822B`（2.93:1）→ `#D17A1F`（白底 3.22:1，色相不变、明度略降）；tokens.json 与 `docs/ux/DESIGN.md` frontmatter 同步（`check:tokens` 校验一致），**例外条目删除**。
- **Arco 实心控件文字**：Arco 2.59 把文字色写死为 `#fff`（24 条规则/32 个选择器）或 `var(--color-white)`，变量层够不到。方案：
  1. 暗色下对「暗色白字不合格」的 **38 个选择器**做**仅 `color`** 的窄覆盖（取 `on-brand` 令牌 `#0B1226`，对 `#7C93FF`=6.62:1），清单在 `tokens.json` 的 `arco.solidTextOnDark`，由生成器写入 `arco-theme.css`（`body[arco-theme='dark'] …` 与 `:root[data-theme='dark'] body …` 两种作用域；无 `!important`；特异性恒高于 Arco）。
  2. 亮色悬停态（Arco 的 5 级）原先白字仅 3.9–4.2:1：`arcoScale` 增加 `solidText` 参数，5 级的底色占比取 [0.2…0] 中第一个使文字 ≥4.5:1 的值。
  3. 禁用态按 WCAG 1.4.3 不要求对比度，保持 Arco 原样（暗色下白字对暗底反而合格）。
- **校验**：`pnpm run check:arco-contrast`（并入 `frontend-lint` 与 `check`）解析 Arco 真实 CSS，对「白字 + 调色板底色」逐选择器、逐主题、逐状态算对比度，并要求覆盖清单**不漏、无死条目**（Arco 升级引入新规则会失败）；7 个自测（含 4 个负向）。**真实 Chromium**：`e2e/selftest.spec.ts` 渲染四种实心按钮（亮/暗、含悬停）用同一审计器量，另有「去掉覆盖则判不合格」的负向对照；截图已核对。
- **例外清单**：`contrast.exceptions` 只剩 `text-disabled`（禁用态，WCAG 1.4.3 不要求；light 3.09、dark 3.87，下限 3 防恶化），理由已改写。
- DESIGN.md「Arco 定制边界」表新增一行允许这类窄覆盖（仅 `color`、清单受脚本校验）。**[ASSUMPTION]** 仍待 UD-14 确认。

### 5. 1.24/1.35/1.37 报告里「本机可做但被推迟」项的复核

- **令牌重置跟随 `secrets.setup_token_hash_file`**（1.35 [ASSUMPTION] 6，原定 1.42）：本机可做，已做。`ResetSetupToken` 读 `server.yaml` 的该键（缺省/空键/文件不存在 → 默认路径；非规范化绝对路径、无法解析、不可读 → 失败关闭且不改动任何文件）。`TestResetSetupTokenFollowsServerYAML`（自定义路径、缺省回落、三种失败关闭、不可读）。
- **TOTP/恢复码刷新后不可找回**：属**刻意设计**（只展示一次，服务端不存明文，不增加任何落盘/回传通道），已写入 `docs/ux/screens.md` §9，并说明各机密丢失后的补救路径（TOTP：登录 Admin 重新绑定；迁移口令：`migrate credential reset`）。
- **`setup-token.hash` 在 `ProtectSystem=strict` 下无法清除**：仍登记为需真实环境，但在 `tools-design.md` §13 写清了判定准则与两种处置（A：单元 `ReadWritePaths`；B：Tools 清理），并给出**没有预先实现 A 的理由**：文件级 `ReadWritePaths` 会 bind mount 固定 inode，使 `--reset` 的原子 rename 失效且 unlink 得 EBUSY；目录级只能「清空」不能「删除」且放宽沙箱写面——效果取决于真实 systemd 的挂载命名空间与 DAC，本机无法验证，未经验证不放宽沙箱。两种处置都不需要改 Server 代码（降级链已在）。另确认：该残留是卫生问题而非安全问题（`install.lock` 存在时所有向导路由先于令牌校验返回 410）。

## 设计偏差

1. **窄覆盖突破了 DESIGN 原「只覆盖 CSS 变量」的字面边界**：Arco 把文字色写死，变量层够不到，只能以 `color` 单属性覆盖；已在 DESIGN 边界表登记，清单受脚本对照 Arco 真实 CSS 校验。
2. **审计范围**：只覆盖「白字 + 调色板底色」的规则（按钮、选中格、徽标、步骤图标、回到顶部、复选框勾等）。Arco 里**非调色板底色的白字组件**（如灰底头像，亮色 `fill-4`）不在本审计内，登记给使用它们的 Story（1.38 起）核对。
3. **句式映射是正则而非结构化字段**：OpenAPI 契约不动（原则上本任务不改），所以不能给响应加 `params`；用「固定句式 + Go 源码样本测试 + 真实 server E2E」把漂移风险压到可检出。
