## Intent

**Problem:** Story 1.11–1.22 的报告里累积了一批「本机能做完、却被留作遗留」的项（11 项）。用户要求现在全部做完；需要 Linux 验收机/MySQL 8.0.16/systemd/Nginx/多机的项继续保持「等待环境验证」，不在本次范围。

**Approach:** 先以代码为准核对每一项的真实现状（已做过的跳过并说明），再逐项实现、测试、更新文档。**没有新增迁移、没有改任何冻结迁移（000001–000018 一字未改，`make migrations-check` 18 个哈希一致）、没有改 OpenAPI/proto**（`tenant.quota_exceeded` 是既有错误码；`x-reauth` 集合不变），因此不需要 `docs/bmad/contract-changes/` 新增 CC 文件。不引入任何 Mock 冒充生产；所有新增集成测试都跑在测试自拉起的独立临时 MySQL/Redis 上（`tests/mysqltest`、`tests/redistest`），本机常驻 mysqld(576/744) 与 redis 未被触碰。

## 逐项处理结果

### 1. `metrics.listen` 非回环：config 层直接拒绝（已做）

- 现状核对：`config.validListen` 只校验「IP 字面量 + 端口」，主机名本来就被拒；非回环 IP（含 `0.0.0.0`、`:9180`、公网/内网 IP）只在 `server.Run` 里告警。
- 先读架构文档：architecture §7 与 tools-design §10.4/§表格都把 Server metrics 定为 `127.0.0.1`，**没有任何「受控的非回环场景」**，ADR 也没有；因此不提供放开开关，直接拒绝。
- 实现：`config.IsLoopbackListen`（127.0.0.0/8、`::1`；空主机/`0.0.0.0`/`::`/主机名/无法解析一律 false）；`validateProblems` 对 `metrics.listen` 非回环报错（含环境变量覆盖，错误文本不回显取值）；`server.Run` 在触碰任何基础设施之前再校验一次（纵深防御：绕过 `Parse` 直接构造的 `Config` 同样拒绝启动），并移除原先的告警分支与 `isLoopbackHost`。`configs/server.example.yaml` 注明。
- 测试：`TestMetricsListenMustBeLoopback`（9 种被拒值 + 3 种允许值 + 环境变量 + `Validate`）；`TestRunRefusesNonLoopbackMetrics`（server 包，6 种配置）；真实二进制 `TestServerRefusesToStart/metrics 监听非回环被拒`（退出码 1、输出含 `metrics.listen` 与「回环」）。

### 2. `server.trusted_proxies` 暴露到配置文件（已做）

- 现状核对：`httpx.Options.TrustedProxies` 存在，但 `server.Run` 构造路由器时没传 → 恒为默认；配置文件没有该项。
- 实现：`config.Server.TrustedProxies []string`（`server.trusted_proxies`，缺省 `127.0.0.1`、`::1`；环境变量 `LINGEDGE_SERVER__TRUSTED_PROXIES` 逗号分隔——为此 `setLeaf` 新增字符串切片支持）；校验：每项 IP 或 CIDR，拒绝未指定地址、`/0`、过短前缀（IPv4 < /8、IPv6 < /32，与 ADR-006 §5 同口径）、zone、空白、IPv4 映射 CIDR、空列表；`server.Run` 把它传给 `httpx.NewRouter`（来源 IP 的唯一来源，访问日志/登录日志与节流/`allowed_cidrs`/审计 ip 都经同一个 `c.ClientIP()` / `httpx.ClientIPFrom`）。示例配置与文档已写。
- 测试：`TestTrustedProxiesConfig`（缺省/合法/环境变量/12 种非法）；`TestTrustedProxiesFromConfigDeterminesSourceIP`（真实 `server.Run` + YAML 配置：缺省与显式本机反代采信 XFF，登录日志与访问日志 `client_ip` 记录真实来源；配置成别的反代时，本机来源的伪造 XFF 被忽略，记录 127.0.0.1）；`TestThrottleAndAllowedCIDRsShareTheSameSourceIP`（可信：同一 XFF 来源同时决定 IP 维度节流与令牌 `allowed_cidrs`；不可信：伪造 XFF 既不能满足白名单，也不能靠轮换 XFF 躲开 IP 节流）。既有 `TestClientIPFollowsTrustedProxies`、`TestAPITokenAllowedCIDRs` 继续覆盖「伪造 XFF 不改变来源 IP / 按链取值」。

### 3. `must_change_password` / 强制 TOTP 未启用账号的 API Token：保持 401，记录为设计决定（已做）

- 现状核对：`apitoken.go` 早已对这两种创建者状态一律 401（ADR-018 §7④：「强制管理员 TOTP 与『须先改密』同样约束令牌（401）」），并有 `TestAPITokenFollowsCreatorLoginPolicy`。
- 评估：「受限放行」对令牌没有可放行的内容——令牌本来就不能调用任何自助 operation（改密、启用 TOTP、再认证都只能 Cookie 会话，ADR-018 §7②），会话的受限放行（只能走启用流程）是靠 Cookie 会话才有意义；若让 401 对调用方「可区分」（例如返回 `password_change_required`），就把「该创建者账号处于须先改密/未启用 TOTP」暴露给持令牌者——令牌持有者与账号所有者未必是同一方（令牌可被转交/泄漏），这是账号状态泄漏，且与 ADR-018 §7⑤「令牌过期、吊销、来源不符、创建者状态异常一律同一个 401、响应不泄漏原因」冲突。
- 决定：**保持现状，写入 ADR-018 修订记录作为设计决定（不再是遗留）**；新增 `TestAPITokenRestrictedCreatorIsIndistinguishable401`：两种受限状态下对 `/admin/users`、`/auth/totp/setup`、`/auth/password/change` 的令牌请求，其 401 响应与「令牌不存在」逐字节一致（去掉 request_id）；同一账号的 Cookie 会话在强制 TOTP 期间仍可调用 `totp/setup`。原因只写服务端日志与 `login_logs.token_auth_failed`。

### 5. 租户视角审计 `actor_label`：改为展示名（已做）

- 实现：`audit/repository.LogRow` 增 `ActorTenantID`、`ActorDisplayName`（联结 users）；`auditapi.ToView` 按上述规则转换；`TenantActorLabel`/`MaskEmail`。

### 6. 令牌创建的配额硬上限（已做；与 6.9 的关系见下）

- 现状核对：`tenant_quotas` 键 `api_tokens` 已在字典内；表语义「默认租户无限制 = limit_value NULL / 无行」；**系统没有另设「默认上限」**（那是产品决定，未被任何文档规定，不虚构）。
- 实现：创建令牌的事务内 `checkAPITokenQuota`：平台令牌不受约束；租户令牌——无配额行或 NULL = 不限；有限额时 `SELECT … FOR UPDATE` 锁住配额行（同一租户并发创建串行化）后统计本租户有效令牌（未吊销且未过期，含所有成员），`>= 限额` → `403 tenant.quota_exceeded`（`details.field=quota_key, reason=api_tokens`，不泄露限额数值）；限额 0 = 禁止创建；轮换不经此检查（新增一枚同时吊销旧的一枚，有效数不变）。租户取自请求 Scope（自助 operation 的 Scope 由主体推导），缺 Scope fail-closed。Repository 方法首参为 `scope.Scope`（满足 repo-check，租户不取自请求参数）。
- **与 Story 6.9 的关系**：6.9 负责配额的通用强制与用量统计（`sites/members/…`、响应里的 `used`）；这里只接线令牌创建这一个硬上限，不引入通用框架，6.9 可把 `LockAPITokenQuota/CountActiveTenantAPITokens` 收编进统一检查，语义（NULL=不限、`>=` 限额拒绝）保持一致。`tests/integration/tenant` 里「`members` 配额 0 仍可加成员」的断言不受影响（本次没碰成员）。
- 测试：`TestAPITokenCreateQuota`（无行/NULL 不限、租户互不影响、平台令牌不受约束、限额 0、吊销/过期释放名额、同租户成员合计、满额时轮换仍成功、并发 10 个创建限额 3 恰成功 3 个且库内有效数 3）。

### 7. 被拒绝类审计（`result=denied`）：防刷方案 + 实现（已做）

- 范围：**只记「已认证主体」的授权类拒绝**——`403 auth.forbidden`、`auth.reauth_required`、`feature.disabled`，环节 `feature/authorize/scope`。**未认证请求（401）、校验失败（400/422）、404（不泄漏存在性）、CSRF 失败（在认证钩子内）、登录失败一律不写 `audit_logs`**：匿名者可零成本制造无限多条，会被用来刷表、淹没真实审计；登录失败仍只写 `login_logs`（它有按 IP/账号的节流与专用保留策略）。
- 防刷：同一 (主体, operation) 在一个窗口内只记一条（默认 60 秒，`[ASSUMPTION]`），并且每个主体每窗口最多 20 条；计数经 `redisx.Limiter`（Redis 跨实例一致，Redis 不可用降级为进程内计数，多实例各记一条可接受）。没有注入 Redis 时整个功能关闭（不是「不去重地写」）。已认证主体因此最多制造「operation 数 × 1」条/窗口，再被主体级上限截断。
- 语义：`action=access.denied`、`resource_type=operation`、`resource_uid=operationId`、`result=denied`（按 database/platform-identity §3.1 的取值）；`changes` 只含环节、错误码、方法、路径模板、路由声明的权限串/功能名（路由元数据，非秘密）；`tenant_id`=主体所属租户（租户管理员能在自己的审计里看到本租户成员的越权尝试，操作者显示展示名）。**不要求与业务事务同提交**（被拒绝的请求没有业务变更，不存在「业务已提交而审计没写」的不一致）；**写入失败只记日志与计数（`DeniedWriteFailures`），绝不影响已确定的 403 响应**——与写操作审计的 fail-closed（审计写不进去 = 业务整体回滚）明确区分。
- 实现：`httpx.DeniedRecorder`（`Auditor` 可选实现的扩展，路由器在渲染 403 之后调用，panic 兜底）；`audit.Writer.RecordDenied`（`denied.go`）；`audit.ActionAccessDenied` + `audit.DeniedActions`（不属于任何 operation 的 Catalog）。
- 门禁扩充（`gates audit`/`make audit-check`）：`audit-denied-catalog`（被拒绝类动作不得登记到某 operation 的 Catalog）、`audit-denied-misuse`（业务代码不得经 `Record` 写被拒绝类动作）、`audit-denied-unrecorded`（`DeniedActions` 登记了动作但 `denied.go` 缺 `RecordDenied/ResultDenied`/动作常量引用）、`audit-const-orphan` 对 `DeniedActions` 的引用核对；`audit_test.go` 增 6 个负向样本。
- 测试（`tests/integration/audit/denied_test.go`，真实 MySQL/Redis）：已认证主体 403 恰一条且归因/来源/变更摘要正确、同窗口重复拒绝只记一条（抑制计数）、不同 operation/不同主体各记各的、`reauth_required` 记录、审计 API 读取与契约；**未认证请求不产生审计行**（无凭据、伪造 Bearer/Cookie、5 次错误口令登录、缺字段登录、缺 CSRF、acting-as 不存在租户 404、他租户资源 404、已认证主体的校验失败——`audit_logs` 总行数前后不变，登录失败仍写 `login_logs`）；窗口过后再记一条；主体级上限（6 个 operation 只记 3 条、另一主体不受影响）与 `feature.disabled` 记录/未认证不记录；写入失败（真实 BEFORE INSERT 触发器注入）响应不变且计数；Redis 被杀（SIGKILL）降级仍记录且去重。

### 8. 跨键约束并发安全（已做）

- 现状核对：`applyCrossField` 在事务**之外**读库、校验，再 `apply` 开事务——并发 PATCH 各自合法、合起来违反。
- 实现：校验移入写事务（`checkCrossKeys`）：本次变更触及任一相关键时，按升序对 4 个相关键行 `SELECT … FOR UPDATE`（当前读）后，以「锁内现值 + 本次变更」校验；并发 PATCH 因此串行化，后到者看到先到者已提交的值。键不存在（取默认值）时 InnoDB 在该位置加间隙锁，并发首次插入的死锁/重复键由 `tx` 既有重试兜住并在重试时重新校验。不触及相关键的变更（品牌、运行模式）不加锁。
- 测试：`TestCrossKeyConstraintsHoldUnderConcurrentPatches`（12 轮 × 2 对键同时竞争：每对恰一个 200 一个 400，最终值恒满足约束）；我把校验临时改回不加锁的读取验证过该测试**确实能抓到**旧缺陷（首轮即「成功 2、拒绝 0」且约束被突破），随后恢复。

### 9. 运行模式跨实例感知：新增 Pub/Sub 用途 `setting_change`（已做）

- 评估：ADR-025 §1 的用途清单已包含「失效广播：`permission_version` 变更、缓存清除的 Pub/Sub」；设置变更的缓存失效属于「缓存清除」；它只在 Server 进程内，不触及数据面（OpenResty/Agent/Node 不访问 Redis，ADR-025 §3，数据面二进制由依赖门禁禁止 import `redisx`）。因此**不破坏**数据面零 Redis 依赖，做。已在 ADR-025 追加修订记录并更新 `docs/operations/redis-degradation.md` 的用途清单。
- 实现：`redisx.PurposeSettingChange`（频道 `le:<env>:sysconfig:setting_change:all`，消息体只有 `changed`，不含任何设置值）；设置服务提交后广播（有损、尽力而为，失败只记 debug）；订阅方收到即丢弃快照；`redisx.Subscribe` 强制的轮询兜底 = 启动/每 30 秒/Redis 恢复时丢弃快照，再叠加快照 TTL（5 秒）——广播丢失最坏仍是一个 TTL。本次不覆盖认证模块自己的 15 秒设置快照（见下「仍保留」）。
- 测试：`TestRunModeChangeBroadcastReachesOtherInstances`（两个独立 sysconfig 实例、各自 Redis 客户端、快照 TTL 设为 1 小时使 TTL 无法掩盖：切换运行模式与 PATCH 品牌都在毫秒级被对端感知）；`TestRunModeChangeFallsBackToSnapshotTTLWithoutBroadcast`（对端 Redis 不可达：TTL 内仍是旧值，证明确实没有广播，随后在 TTL 内最终一致）；`TestChannelPurposes` 增新用途。

### 11. 通用 `PATCH /admin/settings` 的安全敏感键分级再认证（已做）

- 实现：`Def.ReauthRequired` + 清单 `reauthRequiredKeys`：`login.*`（节流窗口/账号阈值/IP 阈值/强制管理员 TOTP）、`auth.*`（会话滑动/绝对过期、再认证窗口、MFA 窗口、令牌默认有效期/上限）、`mail.*`（SMTP 主机/端口/用户名/口令/发件人——改写邮件中继可截获重置口令邮件）、`retention.*`（审计/登录日志保留期，调短 = 缩短取证窗口）、`general.registration_open`。品牌、入口 URL、语言只需 `setting:write`。变更触及任一敏感键（含「恢复默认」与混合批）→ 在写事务之前复用 1.17 的 `httpx.ReauthChecker`（经 `sysconfig.Module.SetReauthChecker(auth.Module.ReauthChecker())` 装配，因为设置模块先于认证模块创建）检查会话的 `reauth_at`，不满足 `403 auth.reauth_required`；Bearer 令牌没有会话，永远不满足，所以令牌不能写这些键，但可写品牌等非敏感键；未装配检查组件或没有主体 fail-closed。顺序：RBAC（`setting:write`）→ 取值校验（400）→ 再认证 → 写入；被拒绝的请求不写设置、不写审计。**OpenAPI 的 `x-reauth` 清单与契约一字未改**，强制在设置服务内，已在 ADR-018 与本文写明。
- 测试：`TestSecuritySensitiveSettingKeysRequireRecentReauth`（20 种敏感写入未再认证全部 403 且不写任何设置/审计，含混合批与恢复默认；非法取值仍 400；非敏感键无需再认证；再认证后可写；会话 `reauth_at` 倒推出窗口后再次被要求；令牌写敏感键 403、写品牌 200）；`TestReauthRequiredKeysAreRegisteredAndPatchable`（清单每个键必须已注册且可 PATCH，防拼写错误让分级静默失效）。既有 sysconfig/audit 集成测试里写敏感键处补了 `adm.Reauth()`（这是适配更严格的行为，不是放宽任何门禁）。

## 仍保留（有理由、不是遗漏）

- **认证模块自己的 15 秒设置快照**（登录节流/会话/MFA/令牌有效期等键）不在广播覆盖内：它们是「调松/调紧安全参数」的缓存，最长 15 秒感知；改成广播需要改认证模块的缓存装配，且这些键已全部纳入再认证分级，风险面小，留给后续（不是本次要求的「运行模式」）。
- **被拒绝类审计的 CSRF 失败**：CSRF 校验在认证钩子内，失败时主体尚未被视为「已认证」，按设计不记（与未认证请求同口径）。
- **被拒绝类审计的限额/窗口数值**（60 秒/20 条）与**令牌配额的默认上限**均为工程取值或不设上限（`[ASSUMPTION]`/产品决定），可经 `audit.Options`/`tenant_quotas` 调整。
