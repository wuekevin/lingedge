## Intent

**Problem:** 配置修订签名（信任域②）与节点 mTLS 私有 CA（信任域③）还没有任何密钥：没有可信根就无法签发修订、无法给节点签发证书，Server 自身的 :9443/:9444 叶证书也没有来源；`deploy.lineage` 不存在导致 1.13 的 `lineage bump` 在新装环境下永远被拒绝；契约里的 `GET /admin/system/signing-keys` 没有实现，且「发行私钥离线、Server 不持有」只是文字约束。

**Approach:** 新增 `internal/platform/signingkeys`（Service：`Initialize`/`Sign`/`List`/`Active`/`CAStatus`/`InitialKeyset` + 路由）与 `pkg/signing`（节点侧复用的纯标准库验证库：修订签名、链式 keyset、指纹、CA 剩余有效期检查）。初始化入口是 **Service 函数**（供 1.24 安装向导/`setup` 调用，本 Story **不注册 `setup` 子命令**、不提前出现），只用 `lingedge_app`。三个信任域用 `gates trustdomain`（源码）与 `tests/security/trustdomain`（真实二进制符号表）双重断言。**没有新迁移**（冻结迁移 000001–000018 一字未改，`make migrations-check` 18 个哈希一致）；契约缺口走 `docs/bmad/contract-changes/CC-10-*.md`（仅加法）。不引入任何 Mock；所有集成测试都跑在测试自拉起的独立临时 MySQL/Redis 上，本机常驻 mysqld(576/744) 与 redis 未被触碰，未用 Docker。

## 权限核对与 AA-7

按最小权限用 `lingedge_app` 实现，**没有权限缺口**：`signing_keys`（000005）与 `system_settings`（000002）对 app 账号有 SELECT/INSERT/UPDATE/DELETE，`audit_logs`（000003）有 INSERT，`system:read` 已由 000004 种子。「每个 purpose 至多一个 active」由 000005 的生成列 `active_key = IF(status='active', purpose, NULL)` 上的唯一索引 `uk_signing_keys_active` 在**数据库层**保证（已核对，无需新迁移）。因此初始化不需要 migrate/maint 账号，对 **AA-7（安装向导的迁移凭据交接，未决）没有任何依赖，也没有私自定稿**：1.24 的向导无论怎样交接迁移凭据，调用 `Initialize` 时都只需要传入 app 池装配出的 Service。

## 逐条验收

### AC1 初始化（`signingkeys.Service.Initialize`）

- 生成 **Ed25519 配置签名密钥**、**ECDSA P-256 私有 CA**（自签、`IsCA`、pathlen=0、CertSign|CRLSign，默认 **10 年**，可配 5–10 年，范围外 `ErrInvalidCAValidity` 拒绝而不是静默截断）、**Server gRPC 叶证书**（ECDSA P-256，由该 CA 签发，`ExtKeyUsage=serverAuth`，SAN = `server_url` 主机名/IP + 设置项 `grpc.tls.san_extra`，有效期 **90 天**，不晚于 CA 到期）。`NotBefore` 回拨 5 分钟以容忍时钟偏差。
- 私钥为 PKCS#8 DER，经 `pkg/secretbox` 信封加密入库，**AAD = `signing_keys|private_key_enc|<行 uid>`**（密文挪行/换列解密即失败）；`enc_key_id` = 当前 KEK；状态 `active`；`key_id` = `cfg-`/`ca-`/`srv-` + SHA-256(公钥) 前 16 位；ed25519 公钥为 32 字节原始公钥，ecdsa 公钥为 PKIX DER；`cert_pem` 存 CA/叶证书（公开内容）。
- **`deploy.lineage=1`**（`group_name=deploy`）在**同一事务**写入，已存在则不改。
- **单事务 + 审计**：密钥入库、lineage、`audit.Record`（新增系统发起的动作 `system.signing_keys.init`，登记在 `audit.SystemActions`，操作者 `system:setup`，变更摘要只含动作名、公开指纹、CA 年数）同一事务，审计写入失败整体回滚、无残留（真实 BEFORE INSERT 触发器注入）。
- **幂等**：某 purpose 已有 active 行则不覆盖；`deploy.lineage` 已存在则不改；全部已存在时不写审计；缺某个 purpose（如叶证书被移除）只补缺失的——CA 已存在则解密旧 CA 私钥签发新叶，用后清零。`server_url`/`san_extra` 之后的变更不改动已签发的叶证书（热重载与 `server.cert_rotate` 轮换属 3.10，**未实现**）。
- **并发安全**：不加锁的「读 → 缺则生成 → INSERT」；并发时后到者在 INSERT 处遇重复键（`uk_signing_keys_active` / `uk_system_settings_key`）或死锁，整体回滚后重试（最多 8 次），重试时读到胜者已提交的行；12 路并发恰有一个报告 Created。
- **缺主密钥拒绝**：`Box` 为空 → `New` 拒绝；`Initialize` 开始前做一次真实的 KEK 加解密往返自检，主密钥不可用（文件缺失/KeyProvider 已关闭）→ `ErrMasterKeyMissing`，**不写任何东西**（含 lineage 与审计）；已初始化后主密钥失效，`Initialize` 与 `Sign` 仍拒绝。
- **`grpc.tls.san_extra`** 新注册为设置键（`THostList`：主机名/IP 字面量列表，可空，≤32 项，规范化去重；可 PATCH、**需再认证**）。

### AC2 签名 API 与验证函数

- `Service.Sign(ctx, manifestBytes)`：`Ed25519(priv, "LINGEDGE-REVISION-V1\n" ‖ manifest 字节)`，记录 `key_id`，**不带过期时间**（无时间参数；同输入重复签名逐字节相同）。私钥只在调用内解密并清零；purpose 与算法必须匹配（只有 `config_signing`/ed25519 行可用于配置签名）。
- 验证在 **`pkg/signing`**（`VerifyRevision`）：只用 ACTIVE/RETIRING key，REVOKED/未知 key 失败，**不读本机时钟**；与 `proto/node-protocol` 一致（`RevisionSignature{key_id, algorithm, signature}`，无过期字段）——核对后无不一致；keyset canonical JSON 的字段编码协议原文未给出，已在 node-protocol §8 澄清并登记 CC-10。`pkg/signing` 只依赖标准库（`TestOnlyStandardLibrary` 断言），不依赖 `internal/*`，不含任何私钥加载逻辑。

### AC3 链式 keyset

`pkg/signing`：`Keyset`/`Key` 数据结构、`CanonicalBody`、`SignKeyset`（签发前用同一套规则自检）、`VerifyRoot`/`VerifyKeysetLink`/`VerifyChain`。规则：版本严格连续（小于等于已信任版本 = 回滚、跳版本 = 断链）；签署者须为上一版 ACTIVE/RETIRING（REVOKED/未知拒绝）；任何内容（公钥/状态/issued_at/追加 key/签名）被改 = 签名失败；保留的 key 算法与公钥不得改变、REVOKED 不得复活；每版至少一把 ACTIVE；失败则整条链作废。`Service.InitialKeyset` 给出信任起点（version=1、previous_version=0、无签名）。轮换流程（签发新版本、重叠期推进、吊销）在 3.10，**未实现**。

### AC4 `GET /admin/system/signing-keys`

经 `httpx.Router.Register` 注册，元数据与 openapi 一致（`system:read`、platform、`x-audit: false`、`x-phase: M1`，权限串已由 000004 种子，`perms-check` 通过），**无 501 占位**；响应类型 `View` 上没有私钥/密文字段，只返回 `key_id/purpose/algorithm/status/public_key/fingerprint/not_after/activated_at/retire_after/revoked_at`；分页同 `/admin/installations`。路由清单 61 → 62 条，`listSigningKeys` 从 M1 未实现清单（138 个）中消失；`/admin/system/signing-keys` 归入已交付模块 `system`。隔离矩阵：platform 路由由骨架统一覆盖（租户 Console 401、租户令牌 403、带 `X-Tenant-ID` 400），本 Story 另显式断言。OpenAPI `SigningKey` 补 `grpc_server`、`public_key`、`fingerprint`、`not_after`（CC-10，仅加法，`openapi-breaking` 无破坏）。

### AC5 三个信任域

- **`gates trustdomain`**（`make security` 的一部分，也是 `gates all` 之一）：扫描 Server 代码路径（`internal/`（不含 `internal/tools`、`internal/testdouble`）、`cmd/lingedge-server`、`pkg/`）的标识符与字符串字面量，以及 `configs/` 示例配置的非注释行，出现加载/持有发行清单私钥（`release|manifest` 与 `private key|secret key|signing key|signer` 同名）或发行清单签名域前缀 `LINGEDGE-MANIFEST-V1` 即失败；扫描范围为空不放行。
- **`tests/security/trustdomain`**：对真实 `go build ./cmd/lingedge-server` 的符号表（`go tool nm`）做同一规则扫描，并断言确为预期二进制（含 `signingkeys.(*Service).list`）。
- **负向样本自测**：门禁 9 个负向样本（加载发行私钥的函数、方法、颠倒命名的调用、变量、3 种字面量、配置行、无法解析）+ 合法写法不误伤 + 范围测试；`tests/gates`（`make gate-selftest`）另在仓库副本里端到端验证「加入加载发行私钥的函数/字面量 → `gates trustdomain` 退出码 1，清理后恢复通过」；符号扫描的负向自测编译一个含 `loadReleasePrivateKey` 的临时程序，扫描器必须抓到。
- `signing_keys.purpose` 的 CHECK 只含 `config_signing|mtls_ca|grpc_server`（测试断言发行用途被拒）。缺主密钥拒绝初始化见 AC1。

## 设计决定与说明

- **系统发起的审计动作**（`audit.SystemActions`）：初始化不是某个 REST operation 触发的（1.24 的 `setupInitKeys` 是未认证的向导路由），不能硬塞进 `audit.Catalog`（门禁要求 Catalog 里的 operation 存在于 openapi 且 `x-audit: true`）。新增独立登记表，门禁 `audit-system-catalog`/`audit-system-unrecorded` 保证「登记了就必须有记录者、且不混进 Catalog」；`Writer.Record` 对系统动作不做「operation 登记」核对，因此 1.24 的向导请求内调用 `Initialize` 不会被拒。
- **`server_url` 不是设置键**（仓库里没有该键，向导采集后 1.24 持久化），故 `InitOptions.ServerURL` 由调用者传入；`grpc.tls.san_extra` 在 docs 里早有键名但无类型定义，本 Story 注册它并补校验。
- **EnsureSetting 先读后插**：连接开启 clientFoundRows，`ON DUPLICATE KEY UPDATE` 的受影响行数无法区分「已存在」，`INSERT IGNORE` 会把其他错误降级为警告，故用普通读取 + INSERT，重复键由整体重试兜住。
- **指纹口径**：配置签名 = SHA-256(公钥)；证书 = SHA-256(DER)（CA 的即 `ca_fp`）。
- **`Sign` 当前没有生产调用者**（修订发布在 3.x），所以真实二进制里它会被链接器裁掉；符号扫描改用必然存在的路由处理函数断言「扫描的是预期二进制」。

## 遗留与风险（只列确属后续 Story 或需 Linux 环境的）

- **ECDSA 私钥的标准库内部副本无法由应用清零**：应用持有的明文字节（PKCS#8 DER、Ed25519 私钥切片）全部在用后清零并由探针测试断言；但 `*ecdsa.PrivateKey` 是标准库对象，Go 1.26 起 `D` 字段已弃用且「修改原始值可能产生无效密钥」，无法可靠清零（已不再尝试触碰 `D`，以免违反标准库约定），对象只在最小作用域内存在、不缓存、不传出包。这是 Go 运行时的已知限制，不是本服务可绕过的；如需更强保证只能依赖 HSM/KMS 型 KeyProvider（ADR-011 的 P5 方向）。
- 叶证书热重载、`server.cert_rotate` 轮换、CA 轮换、keyset 新版本的签发流程与吊销：**Story 3.10**（本 Story 只做数据结构与验证）。
- `setup` 子命令与安装向导的 `POST /public/setup/keys`：**Story 1.24**（调用 `Initialize`；该 operation 的 `x-audit: true` 与 Catalog 登记由 1.24 决定）。
- `doctor` 的 CA 有效期检查项：**Story 1.42** 调用 `pkg/signing.CheckCAExpiry`（函数与 Server 侧 `CAStatus` 已提供并测试）。
- 修订发布调用 `Sign`：Story 3.x（发布与部署）。
