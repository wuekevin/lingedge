# Product Brief: LingEdge（凌界云）

> 本 Brief 由需求基线 V2.0 提炼而成；与基线冲突处以基线为准。无任何市场、竞品或性能数据：基线未提供者一律标注「待确认」，不作估算。深度材料见同目录 `addendum.md`。

## 执行摘要

LingEdge（凌界云，Intelligent Edge Cloud Platform）是一套**独立研发、可自主部署、可商业化运营**的 CDN 边缘云平台，把 CDN 加速、WAF/CC 防护、智能 DNS 调度、四层代理、证书管理与多租户计费收进同一品牌、同一权限体系、同一配置协议之下，由 12 个可独立安装、可组合部署的模块构成（官网、Admin、Console、Server、Node、DNS、Scheduler、Reporter、Worker、Tools、Docs、Status）。

它面向的现实是：想自建或运营一张边缘网络的团队，今天往往要拼装 OpenResty/Nginx 脚本、第三方 DNS、独立证书工具与手工计费，缺少一个统一的控制平面来保证"配置可校验、可发布、可回滚、租户可隔离"。LingEdge 的切入点是把**运维可落地性**做成产品本身：一个 `lingedge` CLI 在宝塔 + systemd 的普通 Linux 服务器上完成安装、升级、回滚与诊断，不依赖 Docker/Kubernetes。

核心判断：这类平台的可信度来自"真实可运行 + 可验证"，而不是界面数量。因此项目以真实节点、真实流量、真实测试为硬约束，禁止 Mock 冒充生产、禁止未经测试宣布完成。

## 要解决的问题

- **运营者**：边缘配置散落在手写 Nginx 文件里，缺少版本、签名、灰度与回滚；节点故障靠人盯；多站点多租户靠约定隔离，易出现跨租户泄漏（缓存、证书私钥、配置）。
- **接入方（站点所有者）**：要在一个控制台里完成域名、源站、缓存、规则、HTTPS、WAF 与日志，并且让源站拿到**正确、不可伪造的真实客户端 IP**。
- **商业运营者**：需要幂等、可对账的用量计量与账单，以及自用/商用两种模式的平滑切换。
- 现状成本（未量化，待确认）：以上为基线所述问题的归纳，基线未给出具体损失数据。

## 解决方案

三层分离、两种运行态：

- **控制平面（Control Plane）**：Go 模块化单体 Server（Gin + sqlx + MySQL 8.0 + Redis 8），负责租户、站点、节点、规则、证书、DNS、发布与计费；Scheduler/Worker 初期内置，可后续独立部署。
- **数据平面（Data Plane）**：OpenResty + Go Node Agent。Agent 经 mTLS 注册、拉取**不可变且已签名的配置版本**，生成配置、`nginx -t`、灰度部署、健康检查，失败回退上一有效版本。**主控离线时，节点按已发布配置继续服务。**
- **观测平面（Observability Plane）**：节点监控、访问日志（独立采集存储，不全部写 MySQL）、探针、告警（去重与恢复通知）、计量。
- **统一规则引擎**：重定向、Rewrite、回源、请求/响应头、缓存、访问控制、限速等共用一套条件/操作符/执行阶段模型，具备优先级、版本、命中统计与回滚。
- **LingEdge Tools**：单一 CLI（含 TUI）负责全组件安装/升级/回滚/备份/诊断，签名清单 + SHA256 校验，取代独立 updater。
- **真实 IP 传递**：站点级自定义"回源向源站传递"的 Header 名，强制覆盖访客伪造值；入站另有独立可信代理 CIDR 机制。

## 差异化（诚实版）

基线未提供竞品对比数据，以下仅是设计取向，不是已验证的护城河：

1. **安装/升级/回滚一体的 Tools**：面向宝塔 + systemd 环境，不要求卸载宝塔、不依赖容器。
2. **"可验证交付"的工程纪律**：Story 完成定义含测试与运行验证；缺环境须标"等待环境验证"。
3. **配置发布的安全模型**：不可变版本、签名、灰度、按节点记录实际生效版本，并禁止把不可信输入直接拼进 Nginx 指令。
4. **自用/商用同一代码体系**：开关商业模块，而非两套产品。

主要依靠执行质量取胜；参考对象（CDN1、Cloudflare、EdgeOne、阿里云 ESA、Certimate）仅取其公开功能与设计理念，不复制闭源代码与专有协议。

## 目标用户

- **平台运营者（主）**：自建/运营边缘网络的团队或个人，使用 Admin 与 Tools，熟悉 Linux/宝塔。成功 = 全新服务器一条 CLI 装好主控与节点，故障可定位、升级可回滚。
- **站点所有者/租户（主）**：通过 Console 接入站点。成功 = 创建站点、绑域名、配源站、申请 SSL、开 WAF/CC、看流量与日志，且看不到他人数据。
- **商业运营/代理商（次）**：套餐、订阅、账单、对账。
- **访客与内容编辑（次）**：官网访问者；官网 CMS 的运营编辑。
- 画像细节与规模为推断，见「假设与待确认」。

## 成功标准

不设数值性能/可用率目标（基线未给，待确认）。以基线第 27 章验收闭环为准，全部须在真实环境验证：

| 闭环 | 通过判据（摘要） |
|---|---|
| A CLI 安装 | 下载 Tools→装主控→Web 初始化→装 Console/Node/DNS→节点注册→状态可查 |
| C CDN | 创建站点→绑域名/源站/节点→证书→DNS 接入→加速→缓存命中 |
| D 规则 | 创建→校验→发布→节点执行→命中可见→更新→回滚 |
| E 真实 IP | 设置 `Ling-Client-IP`→节点自动配置→源站正确识别 |
| J 升级 | 校验包→升级→健康检查→失败回滚→服务恢复 |
| F/G/H/I/B | 调度摘除与恢复、WAF 检测与阻断、计量到对账、CMS 发布与回滚、官网到控制台 |

过程指标：每个 Story 满足基线 DoD；测试结果如实记录，无虚构。

## 范围

**首批优先交付**（基线第 28 章）：LingEdge Tools + Server + 基础 Admin + 官网框架 + 可运行的 CDN Node（对应 Epic 1、Epic 3 核心与 Epic 2 框架）。真实验收："真实网站经 LingEdge 节点访问并正常缓存"。

**随后分阶段**：DNS/调度/Reporter/告警（Epic 4）→ WAF/CC/四层代理（Epic 5）→ 多租户 Console/计费/插件/状态页/文档/全组件发布（Epic 6）。

**明确不做/不承诺**：
- Docker/Compose 作必选组件、Kubernetes 依赖；任意 Shell 执行；Mock 冒充生产；独立 lingedge-updater。
- 大规模 L3/L4 DDoS 清洗（CDN WAF/CC 不等同；高防须对接具备能力的网络）。
- L2 缓存、HTTP/3、DNSSEC、边缘计算：须独立技术验证与后续 Story，不得未测试宣布完成。
- 第一阶段不拆微服务。

## 关键约束

技术栈固定：Go + Gin + sqlx + MySQL 8.0 + Redis 8；Vue 3 + Arco Design Pro（Admin/Console）；Nuxt 3（官网，SSR 须明确 Node.js 运行依赖）；OpenResty；宝塔 + systemd，Linux AMD64/ARM64（Reporter 另含 Windows）。安全与正确性硬约束：租户隔离服务端强制；缓存须防跨用户泄漏；目录/通配符缓存失效须可验证；计费金额禁用浮点且记录幂等可对账；边缘限流不得强依赖每请求访问 Redis；调度摘除须防抖；敏感凭据加密、日志脱敏；生产无固定默认密码。

## 愿景

若成功，LingEdge 成为可由单个团队在普通服务器上落地、也可商业化运营的完整边缘云平台：覆盖 CDN、安全、DNS 调度与计费，并通过插件体系扩展 DNS、证书、支付与通知供应商。2–3 年的具体形态取决于首批真实验收结果，不在此预设。

## 假设与待确认

1. 目标客户画像与首批运营规模未给出（节点数、站点数、租户数）——[ASSUMPTION] 以自运营中小团队为首批。
2. 性能/可用率/SLA 目标未给出，需在 PRD 与性能基线测试后确定。
3. 首版是否同时开放商业模式，还是仅自用模式——[ASSUMPTION] 自用优先，商业模块随 Epic 6。
4. 支付渠道与代理商模式的具体范围未定。
5. 访问日志的独立采集存储选型未定（基线仅要求"独立可扩展、不全进 MySQL"），留待架构 ADR。
6. 缓存目录/通配符/集群级失效的实现方案待技术验证。
7. HTTP/3 方案与 WAF 模块兼容性待验证，首版不承诺。
8. 官网 SSR 与预渲染静态的默认选型及 Node.js 运行依赖的部署形态待定。
9. 自建权威 DNS 冗余与 53 端口冲突处理策略待定（Epic 4）。
10. 是否需要合规项（如备案、数据驻留、支付合规）——基线未涉及，待确认。
11. 并行开发官网与基础平台的前提是 API/数据库契约先冻结，由架构与 OpenAPI 草案保证。
12. 签名/密钥体系（清单签名、配置签名、节点 mTLS CA）的管理与轮换方案待架构阶段设计。
