# PRD: LingEdge（凌界云）

*产品名称已由基线固定：英文 LingEdge，中文 凌界云，定位 Intelligent Edge Cloud Platform。*

## 0. 文档目的与阅读方式

本 PRD 面向产品负责人（用户）、架构/UX/Epic 拆解的下游工作流，以及后续开发代理。它把 **需求基线 V2.0**（`docs/prd/LINGEDGE_V2_REQUIREMENTS.md`，下称「基线」）转写为可验证的功能需求（FR）、跨模块非功能需求（NFR）与验收标准（AC）。

- **权威顺序**：基线 > 本 PRD > Brief。本 PRD 与基线冲突时，以基线为准并记 ADR（基线 §0 头注）。本 PRD 中凡超出基线的内容，均标注 `[ASSUMPTION]` 或列入「决策与假设」（§4），可被用户推翻。
- **追溯方式**：每条 FR/NFR 用「来源：§x」指向基线章节号；§12 给出基线硬性条款（「必须/不得/禁止」）到 FR/NFR 的反向覆盖索引。
- **阶段标签**：`[MVP]`、`[P2]`…`[P6]` 见 §10。未标注者随所属 Feature 的阶段。
- **数值纪律**：基线没有的性能、可用率、SLA、容量、市场数值，一律写「待基线测试后确定」并给出测量方法（§7.6），本文不估算、不虚构。
- 下游：`bmad-architecture`（ADR、ERD、OpenAPI、Node gRPC 协议）、`bmad-ux`（Admin/Console/官网）、`bmad-create-epics-and-stories`（沿用基线 §22 的 Epic 1–6）。

## 1. 愿景

LingEdge（凌界云）是一套独立研发、可自主部署、可商业化运营的 CDN 边缘云平台。它把 CDN 加速、WAF/CC 防护、智能 DNS 调度、四层代理、证书管理与多租户计费，收进同一品牌、同一权限体系、同一配置协议之下，由 12 个可独立安装、可组合部署的模块构成：Website、Admin、Console、Server、Node、DNS、Scheduler、Reporter、Worker、Tools、Docs、Status。

它要解决的是「运维可落地性」：运营者在一台普通的宝塔 + Linux + systemd 服务器上，用单一 `lingedge` CLI 完成安装、升级、回滚、备份与诊断，不依赖 Docker 与 Kubernetes；站点配置以**不可变、已签名、可灰度、可回滚**的版本发布到真实 CDN 节点；租户之间在服务端被强制隔离；主控暂时离线时，节点继续按已发布配置服务访客。

产品可信度来自「真实可运行 + 可验证」，而不是界面数量。因此本 PRD 把基线第 1.3 章的禁止项（Mock 冒充生产、未测试标完成等）升格为跨模块 NFR，并把第 27 章 A–J 闭环写成可逐条验证的验收标准。

## 2. 目标用户

### 2.1 Jobs To Be Done

- **平台运营者**：在全新 Linux 服务器上，不手写 Nginx，也能装好主控与节点；节点故障时知道发生了什么，升级失败时能回到可用状态。
- **站点所有者（租户）**：在一个控制台里完成域名、源站、缓存、规则、HTTPS、WAF/CC、日志；让源站拿到不可伪造的真实客户端 IP；看不到任何他人的数据。
- **商业运营者**：用幂等、可对账的用量记录出账；在自用与商用两种模式间切换，不换代码体系。
- **官网内容编辑**：修改首页与文章，预览、定时发布、回滚，而不碰代码。
- **访客**：通过官网了解产品、查看套餐并注册进入控制台；通过 LingEdge 节点访问被加速的网站。

### 2.2 非用户（v1）

- 需要独立大规模 L3/L4 DDoS 清洗能力的客户（基线 §13.3：CDN WAF/CC 不等于该能力；若提供高防，必须接入实际具备能力的网络或高防服务）。
- 期望以 Docker/Kubernetes 部署的团队（基线 §2.7 明确不使用）。
- 需要边缘计算、HTTP/3 作为生产承诺能力的客户（P6，须独立技术验证）。

### 2.3 关键用户旅程

下列人物为叙述用的示意人物，旅程与基线 §27 闭环 A–J 一一对应，并在 §8 展开为验收标准。

- **UJ-1（闭环 A）陈工在新服务器上装好整张网。** 平台运营者陈工，持有一台干净的 Linux AMD64 服务器和一台宝塔机器。下载 Tools，`lingedge install server`，在浏览器 Web 向导里配置 MySQL/Redis、创建管理员；随后安装 Console、在另一台机器 `lingedge install node` 并 `lingedge node enroll`，再 `lingedge install dns`，最后 `lingedge status` 看到各组件状态。**边缘情况：** 53 端口被 systemd-resolved 占用，安装在冲突检测步骤停下并给出处理选项，而不是静默改动。
- **UJ-2（闭环 B）王先生从官网走到控制台。** 访客王先生打开官网，浏览产品页和套餐页，注册并登录，被带到控制台入口。**边缘情况：** 首页的节点数/可用率若没有真实数据源，页面必须标注为示意信息。
- **UJ-3（闭环 C）林敏让自己的网站走 CDN。** 站点所有者林敏创建站点、绑定域名、设置源站、绑定节点、申请证书、把 DNS 指向 LingEdge，随后访问并在第二次请求看到缓存命中。**边缘情况：** 源站带 `Set-Cookie` 的动态页面不得被缓存给其他访客。
- **UJ-4（闭环 D）林敏为 `/old/*` 加一条重定向规则并回滚。** 创建规则、校验、发布，节点执行并在命中统计里可见，更新后发现误伤，回滚到上一版本。
- **UJ-5（闭环 E）林敏让源站认出真实访客 IP。** 在「网络设置 → 真实 IP 传递」里设置 `Ling-Client-IP`，节点自动重配，源站 Nginx 用 `real_ip_header Ling-Client-IP` 读到正确 IP；访客伪造同名 Header 被覆盖。
- **UJ-6（闭环 F）陈工看着一个节点故障被摘除又恢复。** 节点在线、探测通过；人为制造故障，在满足防抖条件后被摘除并切到备用节点；故障解除后经恢复防抖重新上线；全程有调度日志。
- **UJ-7（闭环 G）林敏调一条 WAF 规则。** 开启规则、用测试请求触发检测，阻断或放行，查看攻击日志，调整规则后再验证；对误拦截有分析入口。
- **UJ-8（闭环 H）赵会计核对一个月的账。** 租户购买套餐、开通、产生用量、计量、出账、付款，对账时原始计量记录与账单金额可逐条追溯，重复上报不重复计费。
- **UJ-9（闭环 I）周编辑改首页。** 修改首页内容，预览，发布，前台更新；发现错误后回滚到上一内容版本。
- **UJ-10（闭环 J）陈工升级节点，失败后回滚。** `lingedge update check` 发现新版本，校验签名清单与 SHA256，升级，健康检查；一次故意构造的失败升级自动回滚，服务恢复。**边缘情况：** 新版本含不可逆 Migration 时，Tools 必须明确告知「不可简单回退二进制」并要求确认（见 R-3）。

## 3. 术语表

下游文档必须逐字使用下列术语，不得引入同义词。

- **平台（Platform）** — 一套 LingEdge 部署整体。包含若干租户、集群。
- **租户（Tenant）** — 资源与数据隔离的最小单位。有用户、站点、订阅、用量与账单。普通租户只能操作已授权资源。
- **站点（Site）** — 租户下的加速对象。拥有若干域名、源站组、规则、缓存设置、TLS 设置、WAF 设置、集群绑定。
- **域名（Domain）** — 站点的访问主机名；一站点可有多个。
- **源站（Origin）/ 源站组（Origin Group）** — 回源目标；一站点可有多个源站与源站组。
- **集群（Cluster）** — 一组节点的服务单元；一集群服务多站点；一节点可加入一个或多个集群。
- **节点（Node）** — 一台运行 Node Agent 与 OpenResty 的边缘服务器。
- **Node Agent** — 节点上的 Go 进程，负责注册、心跳、拉取配置、生成文件、热重载、状态与升级。
- **配置版本（Config Revision）** — 不可变、带签名的完整配置快照。部署（Deployment）把配置版本推送到一组节点；每个节点的「实际生效版本」被单独记录。
- **规则（Rule）** — 统一规则引擎中的一条记录：类型 + 条件 + 动作 + 优先级 + 作用范围 + 状态。
- **执行阶段（Phase）** — 规则引擎固定的请求处理顺序（见 FR-66）。
- **真实 IP 传递（Real-IP Passing）** — LingEdge → 源站方向，把已验证客户端 IP 写入源站可读的 Header（见 §6.9）。区别于入站的**可信代理机制**。
- **主控（Server）** — 中央主控 API，含 Control Plane 全部业务模块；Scheduler/Worker 初期内置其中。
- **自用模式 / 商业模式** — 运行模式开关（D-3）。
- **Tools** — LingEdge Tools，程序名 `lingedge`，唯一安装/升级/运维 CLI。
- **回滚（Rollback）** — 回到上一已验证状态。配置回滚与二进制回滚是两件事；含不可逆 Migration 时二进制不可简单回退（R-3）。
- **访问日志（Access Log）** — 节点产生的逐请求日志，走独立采集存储（D-5），不全部写入 MySQL。
- **rollup** — 对原始指标/日志按时间窗口聚合后的汇总记录（`metric_rollups`）。
- **Mock / Fixture** — 仅用于测试的替身，必须与生产实现严格区分（NFR-1）。
- **等待环境验证** — Story 因测试环境缺失而不能标记完成时的状态（NFR-3）。

## 4. 决策与假设

本章由 PRD 代理在**非交互、无用户确认**的条件下作出。每条「默认决策」都可被用户推翻；「推翻影响」说明被推翻后受影响的范围。D-1 至 D-12 对应 Brief addendum 的 12 项待确认问题；D-13 起为 PRD 阶段新增的决策。

**D-1 目标客户画像与规模** — 决策：首批以**自运营的中小团队/个人**为运营者；不设节点数/站点数/租户数的数值目标。理由：基线与 Brief 均无规模数据，任何数字都是虚构；架构以「模块化单体 + 可拆分」满足基线 §2.1，不提前为未知规模付复杂度。推翻影响：若用户给出规模，应转化为 §7.6 性能基线的目标值并可能触发 Scheduler/Worker/日志存储提前拆分。

**D-2 性能/可用率/SLA** — 决策：**不设任何数值目标**；全部写为「待基线测试后确定」，由 §7.6 定义测量方法；门槛由用户在看到首份基线报告后设定，记 ADR。理由：基线 §23 要求记录性能基线且禁止虚构测试结果；无基线时设数值违反不得虚构原则。推翻影响：无结构性影响，仅需把数值填入 NFR-30 与各 FR 的「待定」处。

**D-3 自用优先、保留商业模式开关** — 决策：首版以**自用模式**交付并验收；`system_settings` 中设运行模式（`self_hosted` 默认 / `commercial`），商业功能（套餐、订阅、订单、充值、余额、代理商、工单、支付、官网价格计费类展示）由开关整体显隐与 API 访问控制；两种模式使用**同一套迁移与代码**，表结构不因模式而异。理由：基线 §16 要求「自用模式关闭不需要的商业功能；商业模式启用完整体系」，§7 允许自用隐藏商业功能，§28 把商业计费列在后序。推翻影响：若要首版即商业化，需把 P5 提前，MVP 范围显著扩大。

**D-4 支付渠道与代理商范围** — 决策：首版（P5 之前）不含任何支付渠道与代理商功能；P5 提供**支付插件接口** + **手工充值/线下对账**路径，具体渠道（如第三方支付）作为插件，由用户届时指定；代理商仅定义数据模型与「代理商—租户」归属与分成**接口占位**，分成规则待用户确认。理由：基线 §16/§6.13 列出能力但无渠道与分成规则；支付合规在基线未涉及（D-10）。推翻影响：P5 范围与插件清单。

**D-5 访问日志采集与存储** — 决策：采用**独立采集路径**，分三层：① 节点本地以带轮转的 JSON Lines 文件写访问日志（不写 MySQL、不经 Redis）；② Node Agent 或独立采集器批量、断点续传地上报到 Server 的日志接收接口，Server 以按「站点/日期」分片的压缩文件落盘并保留本地索引；③ 同时按时间窗口聚合为 `metric_rollups` 写入 MySQL，用于图表、计费、告警。日志写入与查询均经 **LogSink / LogQuery 抽象接口**，后续可无破坏地接入 ClickHouse 等外部存储（触发条件：基线测试显示文件方案无法满足查询或写入需求）。理由：基线 §17.2 只要求「独立可扩展的采集存储，不全部写入 MySQL」，并限定技术栈为 MySQL/Redis；首版用文件 + rollup 不增加新的运维依赖，抽象接口保留扩展性。推翻影响：若用户指定外部存储，LogSink 实现变更，FR-114 的验收不变。保留期与查询延迟目标：待基线测试后确定。

**D-6 缓存目录/通配符/集群级失效** — 决策：首版（MVP）仅提供**精确 URL 刷新**与**站点级整体逻辑失效**（通过缓存键中的「站点缓存版本号」递增实现，旧对象自然过期淘汰）；**目录/通配符/集群级失效**列为 P2，须先完成「前缀版本号 / 缓存键索引」候选方案的 PoC 并通过可验证测试（失效后 100% 抽样请求回源、无误删、有任务回执）才可上线；**禁止**以不受控地扫描删除缓存目录实现。理由：基线 §11 明确要求「设计可验证实现，不得仅靠不受控扫描/删除」；MVP 目标是让真实网站正常缓存。推翻影响：若用户要求 MVP 即含目录刷新，需先交付 PoC 并推迟其他项。

**D-7 HTTP/3** — 决策：首版**不提供且不宣称** HTTP/3；视为 P6 高级能力。准入条件：选定的 QUIC 实现与所选代理及 WAF/规则/缓存/日志模块兼容，并通过「QUIC 下功能等价」测试（规则执行、缓存、WAF 阻断、日志、真实 IP），而非仅握手成功。在准入前，UDP 443 默认不监听。理由：基线 §2.4、§22 明确要求。推翻影响：仅 P6 排期。

**D-8 官网 SSR 与预渲染静态** — 决策：**MVP 官网框架使用预渲染静态站点（SSG）**，由 Nginx 托管，无 Node.js 运行时依赖；**P2 CMS 起默认 SSR**（Nuxt on Node.js，作为 systemd 服务运行于 Nginx 之后），并保留「发布触发重新生成静态」的 SSG 降级模式。Tools 必须检测 Node.js 并**明确声明** SSR 的 Node.js 运行依赖；不得把 Nuxt SSR 当作纯 Go 二进制执行（基线 §21.4）。理由：MVP 官网无 CMS，静态最简；CMS 的预览、定时发布、版本回滚在 SSR 下实现更直接。推翻影响：官网部署形态与 FR-14、FR-44。

**D-9 自建权威 DNS 冗余与 53 端口冲突** — 决策：声明「权威冗余」的最低条件为**至少两个位于不同主机/IP 的 NS 节点**，`lingedge doctor` 对单 NS 部署给出风险告警；安装 DNS 前检测 UDP/TCP 53 占用（含 systemd-resolved 的 127.0.0.53、宝塔内的 named 等），**不自动停用**任何现有 DNS 服务，提供「绑定指定 IP / 由用户确认处理 / 取消」选项；第三方 DNS Provider 模式可作为低风险替代。理由：基线 §21.3 要求考虑冗余与端口冲突。推翻影响：FR-13、FR-92。

**D-10 合规项（备案、数据驻留、支付合规）** — 决策：基线未涉及，**首版不内置**备案、数据驻留、支付合规功能，列入非目标（§9）与开放问题；但提供审计日志、数据保留策略配置与日志脱敏，作为运营者自行合规的基础。推翻影响：若需要，须新增 Compliance 章节与相应 FR。

**D-11 并行开发的契约冻结** — 决策：官网与基础平台**仅在**架构阶段冻结并打标签的 OpenAPI 3.1、gRPC/Protobuf、Migration 结构之后并行；CI 对契约做破坏性变更检测，变更须走 ADR。理由：基线 §26 禁止并行造成 API/库结构不一致。推翻影响：交付节奏。

**D-12 签名与密钥体系** — 决策：划分三个**独立信任域**，各自可轮换：① **发行清单签名**（离线保管的私钥；公钥内置于 Tools，支持多公钥与吊销列表）；② **配置版本签名**（Server 持有；公钥在节点注册时分发，轮换采用新旧并存的重叠期）；③ **节点 mTLS 私有 CA**（Server 管理，节点证书可吊销，节点身份与签名密钥分离）。具体算法与有效期由架构 ADR 决定。**约束**：配置签名不得设置会使离线节点自行停服的过期机制（见 R-4）。理由：基线 §4.8、§10.3、§24。推翻影响：架构 ADR。

**D-13 MVP 租户与控制台** — 决策：MVP 数据模型从第一天起是**多租户**（含租户隔离的服务端强制），但 MVP 运营入口为 **Admin**（运营者以管理员身份代租户操作，默认租户）；**Console 与租户自助注册在 P5**。理由：基线 §28 的 MVP 不含 Console；§24 又要求隔离不可事后补。`[ASSUMPTION]`

**D-14 首批验收环境** — 决策：基线未给出。默认假设：**Linux AMD64（Debian/Ubuntu LTS 与 RHEL 系各一）+ 一台含宝塔面板的服务器 + 一台 ARM64 节点**；MySQL 8.0、Redis 8 为本机或同网段；具体发行版与版本由用户在首次验收前确认。在环境确认前，相应 Story 标「等待环境验证」。`[ASSUMPTION]`

**D-15 GeoIP 与 ASN 数据源** — 决策：规则条件中的 ASN/国家/地区依赖 GeoIP/ASN 数据库，其来源与授权基线未定；MVP 不实现这三类条件的执行，只保留数据模型字段；P3/P4 起启用，数据源作为开放问题 OQ-5。`[ASSUMPTION]`

**D-16 Scheduler/Worker 的安装形态** — 决策：基线 §2.1 说小规模时内置于 Server，§4.2 又把它们列为可安装组件。默认：**内置模式下 `lingedge install scheduler|worker` 返回「已内置于 Server，无需单独安装」并以退出码区分**；独立部署模式在 P3 起提供。基线 §4.3 复选框与 §4.4 命令未列 Scheduler/Worker，视为该默认的体现。

## 6. 功能需求

*FR 全局编号、跨 Feature 稳定。每条 FR 末尾「来源」为基线章节号；「阶段」见 §10。「可验证」条目即验收判据，须在真实环境中执行并如实记录结果（NFR-28）。*

### 6.1 LingEdge Tools（统一 CLI）

**描述：** Tools 是平台的安装、升级、运维唯一入口（程序 `lingedge`，目录 `cmd/lingedge/`）。它不是演示脚本：每个子命令都对真实服务器产生真实效果，并对尚未发布的组件返回明确的「组件尚未发布」退出码，而不是伪造成功。实现 UJ-1、UJ-10。

#### FR-1 统一入口并取代 Updater `[MVP]` — 来源 §2.6、§4.1
`lingedge` 是唯一的安装/升级/运维入口；不开发 `lingedge-updater`。
- 可验证：代码库不存在 `lingedge-updater` 构建目标；所有组件的安装与升级路径均可经 `lingedge` 到达。

#### FR-2 交互菜单与多选安装 `[MVP]` — 来源 §4.3
无参数运行 `lingedge` 进入交互菜单：1 安装组件、2 查看已安装组件、3 升级组件、4 服务管理、5 节点注册、6 系统诊断、7 配置管理、8 备份恢复、9 查看运行日志、10 卸载组件、11 查看版本、0 退出。安装界面为多选复选框（Server / Admin Web / Console / Website / Node / DNS / Reporter / Docs / Status）。
- 可验证：菜单项与基线编号一致；多选后一次执行多个组件安装；终端无 TUI 能力时给出非交互替代提示。

#### FR-3 命令集 `[MVP]` — 来源 §4.4
必须提供：`--help`、`version`、`list`、`status`；`install server|admin-web|console|website|node|dns|reporter|docs|status`；`update check`、`update node`、`update --all`；`service status --all`、`service start|stop|restart node`；`doctor --all`；`config validate`；`node enroll`；`backup create`、`backup restore`；`rollback node`；`uninstall node`。
- 可验证：每条命令在帮助中可见且可执行；对未发布组件（如 MVP 阶段的 `install dns`）返回约定的「组件尚未发布」退出码，不得假装成功。

#### FR-4 非交互、退出码、JSON 与失败恢复 `[MVP]` — 来源 §4.4
所有命令支持交互与无交互模式、明确退出码、JSON 输出、详细日志、参数验证、安装任务锁、执行进度、安装失败恢复。
- 可验证：同一目标并发执行第二个安装任务被任务锁拒绝；`--json` 输出可被 JSON 解析器解析；安装中途 kill 后再次运行可恢复或干净回退，且不破坏既有数据；退出码表在 Docs 中公布。

#### FR-5 组件清单、依赖与资源预检 `[MVP]` — 来源 §4.2、R-5
可安装组件为 server、admin-web、console、website、node、dns、scheduler、worker、reporter、docs、status。必须识别版本依赖、资源要求与端口冲突；允许单机多组件与分布式部署。内置模式下对 scheduler/worker 的安装请求返回「已内置于 Server」（D-16）。
- 可验证：在内存/磁盘不足的环境中安装被预检阻止并说明原因；在已占用目标端口的环境中停在端口冲突步骤；单机同时安装 server + admin-web + website 成功。

#### FR-6 安装流程与不静默覆盖 `[MVP]` — 来源 §4.5
安装必须依次执行：OS 检测、CPU 架构、内存磁盘、端口冲突、宝塔环境、Nginx/OpenResty、MySQL/Redis、组件依赖分析、版本选择、下载签名版本清单、验证清单签名、下载组件包、校验 SHA256 与签名、安全解压、创建运行用户、创建配置目录、安装 systemd Unit、初始化配置、启动服务、健康检查、保存安装状态、输出访问/管理信息。**不得静默覆盖**已有网站、数据库、证书或 Nginx 配置。
- 可验证：在已有同名站点配置/数据库的环境中安装不覆盖，而是中止或要求显式确认；任一步失败有明确报错并可恢复（FR-4）；安装状态被持久化，`lingedge list` 可读。

#### FR-7 宝塔兼容 `[MVP]` — 来源 §4.6、R-10
检测宝塔已装的 Nginx、MySQL、Redis、PHP（仅识别）、站点配置、WAF、防火墙、系统服务；**不得要求用户卸载宝塔**。Node 默认使用**独立 OpenResty 运行环境**，并显式列出端口、配置目录、进程归属。
- 可验证：在含宝塔且其 Nginx 占用 80/443 的机器上安装 Node，Tools 报告冲突并停止，不修改宝塔站点配置；在无冲突机器上 Node 的 OpenResty 与宝塔 Nginx 配置目录、进程互不覆盖。

#### FR-8 升级与回滚 `[MVP]` — 来源 §4.7、R-3
所有组件经 Tools 升级，流程：检测版本 → 获取签名清单 → 检查兼容性 → 下载 → 校验 → 备份当前版本 → 检查数据库迁移 → 安装新版本 → 启动及健康检查 → 成功确认或回滚。存在不可逆 Migration 时，**禁止承诺简单回退二进制即可恢复**：Tools 必须提示、要求显式确认，并把回滚路径定义为「恢复升级前备份 + 旧版本二进制」。
- 可验证：构造一个健康检查失败的新版本，Tools 自动回滚且服务恢复；构造含不可逆 Migration 的版本，Tools 在升级前显示警告并强制备份；回滚后版本号、配置、数据库状态与升级前一致（可逆或备份恢复路径）。

#### FR-9 Tools 安全 `[MVP]` — 来源 §4.8
必须：数字签名验证；禁止未验证发行包；防压缩包路径穿越；防命令注入；Token/密码不进普通日志；不默认删除用户数据；最小权限运行；配置与数据库备份；安全卸载；支持离线安装可信发行包。
- 可验证：篡改清单或包体后安装被拒绝；含 `../` 路径的恶意压缩包被拒绝且无文件越界写入；参数含 shell 元字符不被执行；日志检索不到 Token/密码；卸载默认保留用户数据；离线包经同样签名校验后可安装。

#### FR-10 备份恢复与卸载 `[MVP]` — 来源 §4.4、§4.8
`backup create` 备份配置与数据库；`backup restore` 可恢复；`uninstall node` 为安全卸载，默认保留数据。
- 可验证：备份后清空测试库再恢复，数据一致（NFR-18）；卸载后用户数据目录仍在，除非显式 `--purge`。

#### FR-11 Server 安装与 Web 向导 `[MVP]` — 来源 §21.1、NFR-6
`lingedge install server` 安装 Server、配置、systemd、数据目录与 Web 安装向导：环境检查 → MySQL 配置 → Redis 配置 → 数据库初始化 → 创建管理员 → 系统基础配置 → 内部身份与密钥初始化（FR-26）→ 完成 → 写入 `install.lock`。**不得使用公开固定管理员默认密码。**
- 可验证：全新服务器完成上述流程；`install.lock` 存在后向导不可再次访问；管理员密码由安装者设定，源码与产物中检索不到固定默认口令。

#### FR-12 Node 安装与注册 `[MVP]` — 来源 §21.2、§4.4
`lingedge install node` 安装 Go Agent、OpenResty、Nginx 模板、缓存/日志目录、systemd；`lingedge node enroll` 完成向主控注册（FR-52）。
- 可验证：安装后 Agent 以非 root 最小权限运行（受限于需要绑定的端口，机制由架构定）；enroll 成功后 Admin 节点列表可见该节点在线。

#### FR-13 DNS 安装 `[P3]` — 来源 §21.3、D-9
`lingedge install dns` 安装独立 DNS 服务器，必须考虑权威 DNS 冗余、UDP/TCP 53 端口及与现有 DNS 服务冲突。
- 可验证：53 被占用时安装停止并给出选项而非自动停用占用者；单 NS 部署时 `doctor` 给出冗余风险告警。

#### FR-14 官网安装（SSR 与静态） `[MVP]` — 来源 §21.4、D-8
`lingedge install website` 支持 Nuxt SSR 与预渲染静态站点两种模式；SSR 必须**明确声明并检测 Node.js 运行依赖**，作为独立 systemd 服务管理。**不得把 Nuxt SSR 当成可由纯 Go 二进制执行。**
- 可验证：静态模式在无 Node.js 的服务器上可安装并由 Nginx 托管；SSR 模式在无 Node.js 时安装中止并提示依赖；SSR 模式服务由 systemd 托管并健康检查通过。

#### FR-15 诊断与配置校验 `[MVP]` — 来源 §4.4
`doctor --all` 检查系统环境、端口、依赖、服务、证书到期、配置有效性；`config validate` 校验配置文件。
- 可验证：对故意破坏的配置，`config validate` 以非零退出码报错并指出位置；`doctor` 输出可机读结果。

### 6.2 LingEdge Server（中央主控）

**描述：** Server 是 Go 模块化单体（Gin + sqlx + MySQL 8.0 + Redis 8 + Zap + gRPC），承载 Control Plane 全部业务模块，对 Node/DNS/Reporter 等独立服务提供独立协议。架构为 MVC + Service + Repository + Domain Modules。Scheduler/Worker 初期内置。

#### FR-16 模块化单体与可拆分边界 `[MVP]` — 来源 §2.1、§3.1
第一阶段为模块化单体，**不得无必要拆分微服务**；Node/DNS/Reporter 为独立二进制；Scheduler/Worker 内置但边界清晰，可后续独立部署。Control / Data / Observability 三层之间使用明确接口协议。
- 可验证：架构文档给出模块边界与三层接口；单体可只启动一个进程完成 MVP 全部流程。

#### FR-17 认证 `[MVP]` — 来源 §16、§19
用户注册（商业模式下开放）、登录、会话管理、TOTP 二次验证、登录日志。
- 可验证：登录失败有节流；启用 TOTP 后缺少或错误验证码无法登录；登录事件进入登录日志。

#### FR-18 RBAC 与权限 `[MVP]` — 来源 §6.12、§16
角色、权限、用户-角色、管理员管理；Admin 菜单与 API 都按权限动态裁剪。
- 可验证：无权限角色访问受保护 API 返回统一鉴权错误；菜单随角色变化。

#### FR-19 租户模型与服务端强制隔离 `[MVP]` — 来源 §3.2、§18、§24、NFR-8
Platform → Tenant → Users/Sites/Subscriptions 的数据模型从 MVP 起存在；**租户隔离由服务端强制执行**，不依赖前端；普通租户只能操作已授权资源。
- 可验证：以租户 A 的凭据访问租户 B 的站点、证书、日志、Token 的 API，一律被拒绝（多租户隔离测试，NFR-8）。

#### FR-20 API 通用规范 `[MVP]` — 来源 §19
统一前缀 `/api/v1/`，模块含 auth、admin、tenants、sites、nodes、clusters、dns、cache、waf、certificates、l4、metrics、billing、tasks、public、admin/cms。每个接口必须：认证、鉴权、租户隔离、参数验证、错误码规范、Request ID、审计、分页、API 文档（OpenAPI 3.1）、测试。
- 可验证：随机抽样接口逐项满足；缺少任一项的接口使 CI 失败（契约检查，D-11）。

#### FR-21 异步任务 `[MVP]` — 来源 §19
耗时操作（部署、缓存刷新、证书申请、升级）返回 Task ID，客户端可查询状态与结果。
- 可验证：提交耗时操作立即返回 Task ID；任务状态可从 pending 到 success/failed 查询；失败有原因。

#### FR-22 Migration 与数据库结构 `[MVP]` — 来源 §18
必须使用 Migration；核心表见基线 §18 清单；必须产出完整 ERD、表字段、索引、外键、约束、数据保留策略（NFR-24）、Migration。Migration 须按 R-3 分类（可逆/前向兼容/不可逆）。
- 可验证：空库执行全部迁移成功；迁移测试覆盖升降级路径；每个迁移带分类标记。

#### FR-23 审计日志 `[MVP]` — 来源 §6.12、§17.2、§19
所有管理操作、登录、配置发布、升级、计费变更写入 `audit_logs`，包含操作者、租户、对象、请求 ID。

### 6.7 CDN Node 与配置下发

**描述：** Node 由 Go Node Agent 与 OpenResty 组成：Agent 负责控制，OpenResty 负责 HTTP 处理、反代、缓存及规则/WAF 执行。配置以不可变签名版本下发；主控离线时节点继续服务。MVP 的验收是「真实网站可通过 LingEdge 节点访问并正常缓存」。实现 UJ-3、UJ-4。

#### FR-51 数据面功能 `[MVP]` — 来源 §10.1
节点必须支持：HTTP/HTTPS、HTTP/2、WebSocket、SSE、反向代理、多源站、源站健康检查、静态缓存、Range、缓存刷新/预热、请求/响应/回源 Header 修改、自定义端口、访问日志、性能统计。WAF 与 CC 在 P4。
- 可验证：用真实站点逐项验证（含 WebSocket 升级、SSE 流式不被缓冲破坏、Range 请求返回 206）；HTTP/3 不在此列（D-7）。

#### FR-52 Agent 注册与 mTLS 身份 `[MVP]` — 来源 §10.2、§24
节点使用一次性注册 Token 经 `lingedge node enroll` 向主控注册，获得由主控私有 CA 签发的 mTLS 身份；之后所有节点—主控通信使用 mTLS。
- 可验证：重放已用注册 Token 被拒绝；无有效证书的客户端无法连接节点接口；吊销节点证书后其无法拉取配置。

#### FR-53 心跳与状态上报 `[MVP]` — 来源 §10.2
Agent 周期心跳并上报节点状态（版本、生效配置版本、CPU/内存/磁盘、连接数、OpenResty 状态）；超时判定节点离线并产生事件。
- 可验证：停止 Agent 后节点在判定窗口后显示离线；窗口与阈值可配置，默认值待基线测试后确定。

#### FR-54 配置生成与注入防护 `[MVP]` — 来源 §10.2、§1.3、NFR-5
Agent 基于**模板白名单**生成 OpenResty 配置，所有用户可控值（域名、路径、Header 名/值、正则、源站地址等）必须经校验与转义后进入模板；**禁止直接拼接不可信用户输入生成 Nginx 指令**。
- 可验证：注入测试向量（换行、分号、花括号、`$` 变量、`include`/`lua_` 指令字样）作为域名/Header/路径提交，要么被拒绝，要么被无害转义，且生成配置通过 `nginx -t` 且不含被注入的指令；该测试纳入 CI。

#### FR-55 不可变签名配置版本与下发流程 `[MVP]` — 来源 §10.3
下发流程：主控生成配置 → 校验 → 版本签名 → 节点拉取 → 签名验证 → 生成文件 → `nginx -t` → 灰度部署 → 健康检查 → 确认成功。配置版本一经生成**不可变**；变更产生新版本。
- 可验证：修改已发布版本内容的尝试被拒；节点对签名不符的配置拒绝应用并上报；每步结果记录于 `deployments/deployment_targets`。

#### FR-56 灰度、失败恢复与生效版本记录 `[MVP]` — 来源 §10.3
灰度范围可选（单节点/一批/全部）；任一步失败时节点自动恢复**上一有效版本**；系统**必须记录每个节点实际生效的配置版本**。
- 可验证：下发一个会使 `nginx -t` 失败的配置，节点保持旧版本继续服务并上报失败；Admin 可逐节点看到实际生效版本；灰度时未选中的节点版本不变。

#### FR-57 主控离线时节点继续服务 `[MVP]` — 来源 §3.1、R-4
主控暂时不可达期间，已应用配置的节点必须继续处理访客请求（含 HTTPS、缓存、规则）；节点本地持久化最近有效配置与证书；主控恢复后自动重连、补报状态与日志。
- 可验证：故障注入——停止 Server 或阻断节点到 Server 的网络，持续对节点发起访问，访问成功率不下降；重启节点（主控仍离线）后节点用本地配置恢复服务；主控恢复后节点重新上报。

#### FR-58 独立 OpenResty 运行环境 `[MVP]` — 来源 §4.6、R-10
Node 使用**独立 OpenResty 运行环境**，与宿主机已有 Nginx/宝塔隔离：独立二进制与配置目录、独立 systemd 服务、明确的端口与进程归属。
- 可验证：`lingedge list` 与 `doctor` 输出每个节点的端口、配置目录、进程归属；停止宝塔 Nginx 不影响 Node（在无端口冲突前提下）。

#### FR-59 节点、集群与区域模型 `[MVP]` — 来源 §3.2、§6.4
一节点可按资源与策略加入一个或多个集群；节点具备地域、运营商线路、IP 池、分组、维护状态；站点绑定集群。区域/线路管理的 UI 可在 P3 随调度启用。
- 可验证：同一节点加入两个集群后分别服务各自站点；维护状态的节点不收到新流量调度（P3）且不再被纳入部署目标的健康判定。

#### FR-60 节点升级 `[MVP]` — 来源 §10.2、§4.7
Node Agent 参与软件升级：接收受控升级任务，经 Tools 或 Agent 完成下载、校验、替换、健康检查、回滚（遵守 FR-8、FR-9）。
- 可验证：Admin 触发节点升级任务，节点升级成功并报告新版本；故意失败时自动回滚。

#### FR-61 访问日志产出与性能统计 `[MVP]` — 来源 §10.1、§17.2
节点以结构化格式写本地访问日志（轮转、可限盘），并产出性能统计（请求数、状态码分布、字节数、缓存状态、回源指标）。
- 可验证：日志字段含站点、域名、状态码、缓存状态、字节数、回源耗时、真实 IP；磁盘占用受限制且不会写满系统盘（限额与告警）。

#### FR-62 热重载与进程自愈 `[MVP]` — 来源 §10.2
Agent 对 OpenResty 做热重载（不中断存量连接，重载以 `nginx -t` 通过为前提）并监控进程，进程异常退出时自动拉起。
- 可验证：配置发布时无请求中断（以持续并发请求探测）；kill OpenResty 进程后被自动拉起并上报事件。

### 6.8 统一规则引擎

**描述：** 规则引擎是**一套**统一机制，而不是每种规则一套数据结构。所有规则类型共用同一条件模型、操作符、执行阶段、优先级、版本与回滚。数据模型在 MVP 即完整（含 `site_rules`、`rule_templates`、`rule_versions`）；规则类型的**执行器**按阶段交付（MVP 子集见下）。实现 UJ-4。

#### FR-63 统一规则模型 `[MVP]` — 来源 §8
规则以统一结构存储：类型、条件树、动作、优先级、状态、作用范围、版本；**不得为每种规则类型建立独立的数据结构**。
- 可验证：评审数据库与代码，所有规则类型共用同一张规则表与同一条件模型；新增一种规则类型不需要新表。

#### FR-64 规则类型 `[MVP 子集]` — 来源 §8.1
类型：重定向、URL Rewrite、回源规则、请求头修改、回源请求头、响应头修改、缓存规则、访问控制、页面规则、自定义错误页面、防盗链、限速。MVP 执行器：重定向、URL Rewrite、回源规则、请求头修改、回源请求头、响应头修改、缓存规则、访问控制（IP/CIDR/Path 等不依赖 GeoIP 的条件）、自定义错误页面；页面规则 P2；防盗链与限速 P4（随 WAF/CC）。
- 可验证：MVP 每种已交付执行器在真实节点上被验证；未交付类型在 UI 与 API 中不可创建（不假装可用）。

#### FR-65 匹配条件与操作符 `[MVP 子集]` — 来源 §8.2、D-15
条件字段：Host、Path、URI、Query、HTTP Method、Header、Cookie、User-Agent、Referer、客户端 IP、CIDR、ASN、国家、地区；操作符：eq、ne、contains、starts_with、ends_with、regex、in、not_in、exists、ip_in_cidr；支持 AND/OR/NOT 组合。ASN/国家/地区字段 P3/P4 启用（D-15）。
- 可验证：每个字段×适用操作符有单元测试；嵌套 AND/OR/NOT 组合的真值表测试通过；regex 须受长度/复杂度限制，防止 ReDoS（FR-68）。

#### FR-66 执行阶段 `[MVP]` — 来源 §8.3
执行顺序固定为：真实 IP 识别 → 访问控制 → WAF/CC → 重定向 → URL Rewrite → 缓存规则 → 缓存查询 → 回源规则 → 回源 Header → 源站响应 → 缓存写入 → 响应 Header → 返回客户端。
- 可验证：构造同时命中多个阶段规则的请求，观察执行顺序与基线一致（集成测试）；WAF/CC 阶段在 P4 前为空阶段但顺序位置保留。

#### FR-67 规则生命周期属性 `[MVP]` — 来源 §8.3
每条规则具备：优先级、启用状态、作用范围、配置版本、命中统计、发布记录、回滚能力。
- 可验证：同条件下优先级高者先执行；停用规则不执行；命中次数可在 Admin 查询且与访问日志抽样一致；回滚到任一历史规则版本后节点生效（闭环 D）。

#### FR-68 规则校验 `[MVP]` — 来源 §8、§10.3、NFR-5
规则在发布前被校验：结构合法、操作符与字段匹配、正则可编译且受限、Header 名合法、重定向目标合法、无循环；校验失败阻止发布并给出可读原因。
- 可验证：非法规则无法发布；校验通过的规则在节点生成配置时仍受 FR-54 约束。

#### FR-69 缓存规则与动态内容隔离 `[MVP]` — 来源 §8.3、§11、NFR-5
规则引擎必须解决**缓存规则与动态内容隔离**问题，避免跨用户缓存泄漏：默认不缓存带 `Set-Cookie` 的响应与带 `Authorization` 的请求；缓存键纳入受控的 Query/Header/Cookie 维度；`Vary` 被正确处理；缓存规则无法违反上述默认，除非站点管理员显式选择并被审计且在界面给出风险提示。
- 可验证：两个带不同会话 Cookie 的用户请求同一动态 URL，用户 B 不会收到用户 A 的缓存响应（泄漏测试，NFR-8 同类）；该测试纳入 CI。

### 6.9 真实客户端 IP 传递（已确认强制需求）

**描述：** 方向是 **LingEdge → 用户源站**：站点所有者自定义「向源站传递真实客户端 IP 的 Header 名称」。这不是让用户定义 LingEdge 从上游读取哪个 Header。后台位置：网站管理 → 选择站点 → 网络设置 → 真实 IP 传递。例：已验证客户端 IP 为 1.2.3.4 时，向源站发送 `X-Real-IP: 1.2.3.4`、`X-Forwarded-For: 1.2.3.4`、`Ling-Client-IP: 1.2.3.4`；源站 Nginx 配置 `set_real_ip_from <可信 LingEdge 边缘出口 IP>` 与 `real_ip_header Ling-Client-IP`。实现 UJ-5。

#### FR-70 站点级真实 IP 传递配置 `[MVP]` — 来源 §9.1、§9.2
配置项：X-Forwarded-For 开关、X-Real-IP 开关、自定义 Header 开关、自定义 Header 名称（如 `Ling-Client-IP`）、XFF 传递策略、配置发布状态；**每个站点独立配置**。
- 可验证：两个站点分别配置不同 Header 名，各自的回源请求只含各自配置的 Header；入口位于「网站管理 → 网络设置 → 真实 IP 传递」。

#### FR-71 回源 Header 写入与覆盖 `[MVP]` — 来源 §9.3、§9.4
节点向源站发送所配置的 Header，值为经验证的客户端 IP。**自定义 Header 必须覆盖访客伪造的同名值**；X-Real-IP 同样以验证结果覆盖。XFF 传递策略至少提供「覆盖为真实 IP」与「在可信链路上追加」两种 `[ASSUMPTION: 具体选项名由架构定]`。
- 可验证：访客自带 `Ling-Client-IP: 6.6.6.6`，源站收到的是真实 IP 而非 6.6.6.6；对 `X-Real-IP`、`X-Forwarded-For` 做同样的伪造测试；开关关闭的 Header 不被发送。

#### FR-72 Header 名称合法性与保留名限制 `[MVP]` — 来源 §9.4、NFR-5
**Header 名称必须合法**（符合 HTTP token 语法、有长度上限）；**禁止使用敏感保留 Header**（如 Host、Content-Length、Transfer-Encoding、Connection、Upgrade、Cookie、Set-Cookie、Authorization 等；完整清单由架构给出）；校验失败阻止保存。
- 可验证：非法字符、过长名称、保留名称均被拒绝并给出原因；含换行/冒号的名称不能进入生成配置（FR-54）。

#### FR-73 来源可信、发布、回滚与调试 `[MVP]` — 来源 §9.4
写入 Header 的 IP **必须来自可信的识别结果**（FR-74 的输出）；该配置随站点配置版本下发、可回滚；提供调试能力（例如在 Admin 显示节点对一次测试请求识别到的 IP 与最终传递的 Header）。
- 可验证：修改 Header 名后产生新配置版本，节点生效后源站可见新 Header；回滚后恢复旧名；调试视图与源站实际收到的一致。

#### FR-74 入站真实 IP 的可信代理机制 `[MVP]` — 来源 §9.4、§8.3
LingEdge 自身**入站**真实 IP 识别必须有独立的可信代理 IP/CIDR 机制（用于前置有其他代理/CDN 的场景）：仅当连接来自可信代理时才采信其转发的客户端 IP Header，否则使用 TCP 对端地址。
- 可验证：来自非可信地址的请求携带伪造 `X-Forwarded-For` 时，识别结果仍是其 TCP 对端地址；来自配置的可信 CIDR 的请求被正确采信；可信列表可按站点或集群配置。

### 6.10 缓存系统

**描述：** 初期使用成熟的 OpenResty/Nginx 缓存。核心难点是**安全**（不跨用户泄漏）与**可验证的失效**。实现 UJ-3。

#### FR-75 缓存策略配置 `[MVP]` — 来源 §11
可配：默认策略、路径规则、文件类型、TTL、Query 参数策略、Cookie 策略、Cache Key、状态码缓存。
- 可验证：为静态资源设置 TTL 后第二次请求命中；按 Query 参数策略（忽略/全部/白名单）时命中行为符合配置。

#### FR-76 Cache Key 与隔离 `[MVP]` — 来源 §11、§8.3、FR-69
Cache Key 至少含站点、Host、Scheme（按策略）、规范化 URI 与受控 Query 维度，并含「站点缓存版本号」（支撑 D-6 的整站逻辑失效）。
- 可验证：同一 URL 在两个站点间不共享缓存；递增站点缓存版本号后旧对象不再被命中。

#### FR-77 缓存锁、Range 与大文件 `[MVP]` — 来源 §11、§10.1
支持缓存锁（并发回源合并）、Range 缓存、大文件缓存；大文件的切片/回源行为受参数控制。
- 可验证：并发 N 个请求同一未命中对象时只产生一次回源（缓存锁）；Range 请求命中缓存返回正确的 206；大文件缓存阈值可配。

#### FR-78 URL 刷新与预热 `[MVP: URL 刷新；P2: 预热]` — 来源 §6.7、§11
按精确 URL 刷新缓存；预热通过受控任务拉取指定 URL。任务经异步 Task（FR-21）分发到目标节点，并记录每节点结果（`cache_tasks`、`cache_task_nodes`）。
- 可验证：刷新后下一次请求回源且返回新内容；任务回执列出每个节点成功/失败；预热后首次访问命中。

#### FR-79 目录、通配符与集群级失效 `[P2，PoC 通过后]` — 来源 §11、D-6
**必须设计可验证的实现，不得仅靠不受控扫描/删除缓存目录。** 候选方案：前缀版本号或缓存键索引；须先 PoC。
- 可验证：PoC 报告证明失效后抽样请求 100% 回源、无关路径不受影响、任务有每节点回执；在 PoC 通过前，目录/通配符入口在 UI/API 中不可用。

#### FR-80 磁盘限制与缓存统计 `[MVP]` — 来源 §11、§6.7
可配缓存磁盘限额；统计命中率、命中/未命中/过期/绕过比例；缓存磁盘使用可见。
- 可验证：达到限额后淘汰生效而不写满系统盘；命中率统计与访问日志抽样一致。

#### FR-81 L2 中间缓存 `[P6]` — 来源 §11、§22、R-7
L2 缓存属高级能力，须独立技术验证与 Story，不得未经测试宣布完成。
- 可验证：未通过验证前，Admin「L1/L2 缓存」菜单中 L2 不可启用，文案不宣称可用。

### 6.12 DNS 与智能调度（P3）

#### FR-89 记录类型与线路 `[P3]` — 来源 §12.2、§6.6
记录类型：A/AAAA/CNAME/TXT/MX/CAA/SRV/SOA/NS；GeoDNS、运营商线路、权重。
- 可验证：不同来源（地域/运营商）的查询返回不同的节点 IP；权重分配与配置吻合（统计检验）；每种记录类型有解析正确性测试。

#### FR-90 调度策略 `[P3]` — 来源 §12.3、§6.5
调度综合：节点健康、地域、运营商、带宽余量、延迟、错误率、权重、维护状态、容量。具备备用节点池与流量迁移。

#### FR-91 故障摘除与恢复防抖 `[P3]` — 来源 §12.3

- 可验证：单个探针一次失败不触发摘除；满足联合条件才摘除；恢复需连续成功；全过程记录于调度日志（闭环 F）。

#### FR-92 DNS 冗余、端口冲突与滥用防护 `[P3]` — 来源 §21.3、§24、D-9、NFR-16

### 6.14 WAF 与 CC（P4）

**描述：** WAF/CC 在 OpenResty/Lua 中执行，位于规则引擎的「WAF/CC」阶段（FR-66）。基础访问控制（IP/CIDR/路径等）在 MVP 以访问控制规则提供（FR-64）；本节为完整安全中心。实现 UJ-7。

#### FR-96 WAF 检测与托管规则 `[P4]` — 来源 §13.1、§6.8
检测 SQL 注入、XSS、路径遍历；托管规则集 + 自定义规则；规则动作：阻断/放行/记录。
- 可验证：对标准攻击样本集，规则按配置阻断或仅记录（观察模式）；对一组合法业务请求样本的误拦截率被测量并如实记录（WAF 误拦截测试，§23）；规则变更经配置版本发布与回滚。

#### FR-97 访问限制与 Bot 防护 `[P4]` — 来源 §13.1
IP 黑白名单、ASN 封禁、国家地区限制、UA/Referer 限制、Bot 防护。
- 可验证：每类限制有正反两侧的真实请求验证；ASN/国家/地区依赖 GeoIP 数据源（OQ-5）。

#### FR-98 CC 防护与边缘限流 `[P4]` — 来源 §13.2、R-9
支持单 IP 限速、IP+URI 限速、API 路径限速、站点整体限速、临时封禁。**边缘限流必须避免 Redis 成为每次请求的强制远程依赖**：计数在节点本地进行，跨节点汇总异步；跨节点总量为近似值，不保证精确全局配额。
- 可验证：断开 Redis（或主控）后限流仍在节点本地生效且请求延迟不显著恶化（以基线测试对比，阈值待定）；限速命中产生事件。

#### FR-99 挑战、观察模式与例外 `[P4]` — 来源 §13.2
JS Challenge、CAPTCHA、观察模式（只记录不阻断）、规则例外（按路径/IP/Header 等）。
- 可验证：观察模式下命中仅记录；例外规则使指定请求绕过相应规则；挑战通过后在有效期内不重复挑战。

#### FR-100 安全事件、日志与误拦截分析 `[P4]` — 来源 §13.1、§6.8、§17.2
记录安全事件、攻击日志，并提供误拦截分析入口（按规则/路径/来源聚合，支持一键加例外）。
- 可验证：阻断事件出现在安全事件列表，含规则 ID、请求摘要（敏感值脱敏）；误拦截分析能列出被拦截的合法请求候选。

#### FR-101 安全边界声明 `[P4]` — 来源 §13.3、R-13
**必须说明** CDN WAF/CC 不等于具备独立的大规模 L3/L4 DDoS 清洗能力；若提供高防，必须接入实际具备能力的网络或高防服务。该声明出现在官网安全产品页、Docs 与 Console 安全防护页。
- 可验证：上述三处均有该声明；评审清单检查通过；文案不出现未经证实的防护量级承诺。

### 6.15 四层代理（P4）

#### FR-102 TCP 应用 `[P4]` — 来源 §15、§6.9

- 可验证：TCP 流量经节点转发到真实后端；后端宕机被健康检查摘除。

#### FR-104 四层通用控制与统计 `[P4]` — 来源 §15、§6.9
源 IP 访问控制、PROXY Protocol、连接日志、带宽与流量统计。**TCP 与 UDP 须分别定义配置及健康检查语义；不得套用 HTTP 缓存与规则机制。**
- 可验证：L4 应用在数据模型与 UI 中不出现缓存/HTTP 规则选项；PROXY Protocol 开启时后端收到正确的原始地址；连接日志与流量统计可查。

## 7. 跨模块非功能需求

*NFR 全局编号。凡「不得/禁止」均为硬性要求，违反即视为缺陷。性能与可用率数值一律「待基线测试后确定」，测量方法见 §7.6（D-2）。*

### 7.1 交付纪律（基线 §1.3、§25）

- **NFR-1 禁止 Mock 冒充生产** — 不得用 Mock API 冒充真实接口；不得用模拟节点代替真实 CDN 节点；不得用虚假流量/安全数据冒充生产指标。允许测试 Mock/Fixture/模拟服务器，但**必须与生产实现严格区分**：位于测试目录或测试构建标签内，生产构建产物不可达。验收类证据（§8）必须来自真实组件。来源：§1.3、R-11。
  - 可验证：生产构建产物中检索不到 Mock 包与固定的假数据；CI 有检查「生产构建不得引用测试替身」。
- **NFR-2 不得空壳交付，每阶段可运行** — 不得只生成前端页面而不实现业务；不得只建目录和空接口就宣称完成；不得一次性堆砌不可运行代码；每个阶段必须产出可运行、可验证的交付物。来源：§1.3。
  - 可验证：每个阶段末有一个从零部署可运行的版本与对应验收记录；空实现的接口在 API 文档中不被标为已交付。
- **NFR-3 Story 完成定义（DoD）** — 未测试不得标记 Story 完成。DoD 全部满足才算完成：需求明确、代码完成、编译通过、数据库迁移完成、API 可调用、前端功能可用、权限正确、单元测试通过、集成测试通过、关键异常测试通过、文档更新、运行验证完成。**测试环境缺失时必须标记「等待环境验证」，不得写成已完成。** 来源：§1.3、§25。
  - 可验证：Story 状态流转包含「等待环境验证」；抽查已完成 Story 均有测试与运行证据。
- **NFR-4 不得绕过认证、权限、租户隔离** — 任何接口、任务、后台作业、插件都不得绕过。来源：§1.3、§24。
  - 可验证：自动化遍历全部路由检查认证/鉴权/租户校验中间件；新增路由缺失则 CI 失败。
- **NFR-5 不可信输入不得拼接生成 Nginx 指令** — 见 FR-54，覆盖域名、路径、Header、正则、源站地址、错误页内容、Lua 片段等一切用户可控值。来源：§1.3、§24。
  - 可验证：配置注入测试向量集（FR-54）通过。
- **NFR-6 生产无固定默认密码** — 任何组件（Server、数据库初始化、Node、DNS）生产环境不得使用固定默认口令；初始凭据由安装者设定或一次性随机生成并强制修改。来源：§1.3、§21.1。
  - 可验证：代码、配置模板、迁移与文档中检索不到默认口令。
- **NFR-7 Docker 非必选，不依赖 Kubernetes** — 任何组件的安装与运行不得以 Docker/Compose/K8s 为必要条件。来源：§1.3、§2.7。
  - 可验证：在无 Docker 的服务器上完成全组件安装与验收。

### 7.2 安全（基线 §24、§18）

- **NFR-8 租户隔离服务端强制** — 隔离在服务端的 Repository/Service 层强制（查询必带租户条件），不依赖前端；定期运行多租户隔离测试，覆盖站点、规则、证书/私钥、日志、Token、账单、工单、缓存任务。来源：§18、§24、§16。
  - 可验证：隔离测试矩阵（资源×操作×身份）全绿；任一越权用例失败即阻断发布。
- **NFR-9 注入类防护** — SQL 注入（参数化 sqlx）、XSS（输出转义、CSP）、CSRF（会话类接口防护）、命令注入（不使用 shell 拼接，调用外部程序用参数数组）。来源：§24。
  - 可验证：安全测试包含各类攻击样本；静态检查禁止拼接 SQL 与 `sh -c` 拼接。
- **NFR-10 SSRF 防护** — 所有由用户输入触发的出站请求（回源地址、Webhook、ACME/Provider 回调、预热 URL、健康检查目标）必须经地址校验，默认拒绝回环、链路本地、内网与元数据地址，且在连接时校验解析结果以防 DNS 重绑定；例外须显式白名单。来源：§24。
  - 可验证：对内网/元数据地址与 DNS 重绑定的测试被拒。
- **NFR-11 路径穿越与 Header 伪造** — 文件路径类输入（上传、解压、日志下载、静态资源）防路径穿越；来自访客的转发类 Header 在不可信链路上不被采信（FR-71、FR-74）。来源：§24。
  - 可验证：`../`、绝对路径、符号链接测试向量被拒；伪造 Header 测试通过。
- **NFR-12 敏感凭据加密与日志脱敏** — 敏感凭据（Provider 凭据、SMTP/Telegram 凭据、证书私钥、API Token、节点密钥）加密保存；日志与审计中密码、Token、私钥、完整凭据脱敏。来源：§24、§4.8。
  - 可验证：数据库中无明文凭据；日志扫描检测不到敏感模式；密钥加密主密钥的保管与轮换由 ADR 定义。
- **NFR-13 证书私钥保护** — 私钥仅在需要处解密，节点上以最小权限文件保存，不经普通日志与 API 回显。来源：§24、§14。
  - 可验证：节点上私钥文件权限仅限运行用户；API 无私钥回显。
- **NFR-14 节点身份与最小权限** — 节点以 mTLS 身份认证；**不得将全部节点控制权限暴露给普通租户**：租户只能通过站点/规则等抽象影响节点，不能直接操作节点或下发任意文件/命令。来源：§24、§10.2、§6.16。
  - 可验证：租户 Token 调用节点管理类接口被拒；节点内部接口不接受租户凭据。
- **NFR-15 软件供应链** — 发行清单与包签名与哈希校验（FR-9）；依赖锁定、构建可复现性目标与第三方依赖清单（SBOM）`[ASSUMPTION: SBOM 为本 PRD 补充要求，用户可否决]`。来源：§24、§4.8。
  - 可验证：发布流水线产出签名清单；篡改任一发行包被 Tools 拒绝。

### 7.6 性能与可用率：测量方法（数值待基线测试后确定）

- **NFR-30 性能基线** — 基线未给出任何性能数值，本 PRD **不设数值目标**。在 MVP 完成后产出首份《性能基线报告》，再由用户据此设定门槛并记 ADR。测量方法：
  - 记录参考环境（CPU/内存/磁盘/网卡/内核/OpenResty 版本/源站规格/网络条件）。
  - 压测工具与参数可复现（候选：wrk、h2load、k6）；每个场景预热后重复多次，报告中位数与离散度，保留原始数据。

  - 记录未通过项与已知问题，如实记录，不修饰（NFR-28）。
  - 可验证：基线报告存在且满足上述字段。
- **NFR-31 可用率/SLA** — 基线与 Brief 均无可用率或 SLA 目标，不作承诺；官网/Status 的可用率展示只来自真实监控（FR-41、FR-121）。可用率目标待基线测试后由用户确定。
  - 可验证：任何对外可用率数字均能追溯到真实监控数据源。
