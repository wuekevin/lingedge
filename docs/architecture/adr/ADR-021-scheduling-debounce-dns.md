# ADR-021 智能调度与 DNS 架构：多源联合判定 + 迟滞防抖（P3 预案）

- 状态：已接受（预案；架构代理非交互决策）｜日期：2026-11-16｜关联：基线 §12、§21.3；PRD FR-87..95、D-9、D-15、R-2、R-8、NFR-16、OQ-5；architecture AD-21｜阶段：P3

> **预案，进入该阶段前须 PoC 复核。** 本 ADR 固定方向与不变量，以便 M1 的数据模型/协议预留；具体阈值全部「待基线测试后确定」。

## 背景

基线 §12.3：调度综合节点健康、地域、运营商、带宽余量、延迟、错误率、权重、维护状态、容量；**必须有故障摘除与恢复防抖，不能仅依据单个探针一次失败摘除节点。** 基线 §12.1：A 第三方 DNS Provider、B 自建权威 DNS（miekg/dns + MySQL + Redis）。D-9 要求权威冗余至少两个位于不同主机/IP 的 NS，且不得自动停用占用 53 端口的服务。

## 决策

1. **组件分工**：
   - `scheduler` 模块（Server 内置角色，P3 起可独立，ADR-019）计算**每个站点/记录集的有效节点集合**并产出 DNS 记录变更；
   - `lingedge-dns`（独立二进制）从 Server 经 gRPC mTLS 拉取 Zone 快照（包 `lingedge.dns.v1`，P3 才定义 proto，沿用 ADR-003 身份体系，证书 role=`dns`），本地以内存 + 快照文件应答，**Server 离线时继续按最后快照应答**（与 ADR-020 同理）；
   - `lingedge-reporter` 多区域探测上报 `probe_results`；
   - Provider 模式：经统一 `DNSProvider` 接口（Cloudflare/阿里云 DNS/DNSPod 为插件，凭据加密，ADR-011）同步记录，同步为可重试任务 `dns.sync`。
2. **健康输入（多源）**：① Reporter 多区域探测（HTTP/HTTPS/TCP/TLS/DNS 类型，FR-94）；② 节点心跳与 Agent 本地数据（连接数、错误率、带宽余量）；③ 源站健康（`origin_health`）；④ 维护状态（人为）。**任何单一来源不能独自触发摘除。**
3. **摘除判定（迟滞）**：节点被判不健康需同时满足：(a) 来自**至少 K 个不同探测区域/探针**（共 M 个中）在**连续 N 个探测周期**均失败，且 (b) 心跳/本地状态不与探测矛盾（例如探针失败但节点心跳显示健康且仅个别区域失败 → 标记「降级/区域性」而非全局摘除）。K、M、N 与探测周期均为配置，默认值待基线测试后确定。
4. **恢复判定**：恢复上线需**连续 N' 个周期**成功（来自 ≥K' 个区域），且满足**最短摘除保持时间**（hold-down，避免立刻回切）；恢复后以**渐进权重**（如从低权重爬升）重新引流。
5. **抖动抑制**：单位时间内同一节点状态翻转超过上限 → 进入「人工锁定」并告警，直到运营者确认；全局保护：**池内健康节点数低于最小阈值时不再摘除**（fail-static，保持现状并告警），避免探针故障导致全站解析为空；全部不健康时返回全部节点（best effort）并告警，而不是空应答。
6. **决策可审计**：每次摘除/恢复/切换写调度日志（输入证据：哪些探针、哪几次结果、阈值），Admin 可查（基线 §6.5「调度日志」）；产生告警并去重，恢复发恢复通知（FR-117）。
7. **选路因子**：地域/运营商线路（GeoIP/ASN 数据源待 OQ-5，D-15）、权重、带宽余量、延迟、错误率、容量、维护状态；先过滤不可用节点，再按线路匹配，再按权重/容量加权；备用节点池在主池不足最小阈值时启用。
8. **DNS 服务不变量**：UDP+TCP 53；响应限速与对 ANY 等的处理策略防放大（NFR-16、FR-92）；管理接口仅经 Server 的鉴权 API 修改 Zone；记录变更带 serial 并在多 NS 间一致；DNS TTL 与摘除生效延迟的关系须在文档中如实说明（缓存解析器可使旧记录持续存在）。
9. **端口冲突与冗余**：安装前检测 UDP/TCP 53（含 `127.0.0.53`、宝塔 `named`），**不自动停用**；`doctor` 对单 NS 部署告警（D-9、R-2）。
10. **DNSSEC 不在本 ADR**（P6，R-8，须独立验证）。

## Binds / Prevents / Rule

- 约束：scheduler/dns/reporter/monitoring 模块实现、P3 的数据库表（`scheduling_policies`、`node_pools`、`health_checks`、`probe_results`、`dns_*`）。
- 防止：单探针抖动导致整站摘除；摘除后反复回切（flapping）；探针故障引发全站不可解析。
- 规则（AD-21）：**摘除/恢复必须多源联合判定 + 迟滞（连续次数、最短保持、渐进恢复），并保留最小健康节点下限。**

## 备选方案与权衡

- **单探针失败阈值（如连续 3 次失败即摘除）**：否决——违反基线 §12.3；单探针网络问题会误摘。
- **仅依赖节点心跳判定健康**：否决——心跳正常不代表对外可达（路由/运营商问题），且节点自报不可作为唯一证据。
- **DNS 节点直连 MySQL 读 Zone**：否决——扩大数据库暴露面，不满足「Server 离线时继续应答」；快照拉取更稳健。
- **不设最小健康下限、完全自动**：否决——探测系统故障会放大为全面中断。

## 后果

- 多区域探针部署与运维成本；少于 K 个探针区域时判定退化（须配置感知并告警）。
- 防抖带来摘除延迟（权衡误报与响应速度），具体数值待基线测试。
- GeoIP/ASN 数据授权与更新机制未定（OQ-5）。

## 可被推翻处

用户可选择 Provider 模式作为唯一 DNS 方案（降低 53 端口与冗余运维成本）：则 `lingedge-dns` 推迟，调度输出经 `dns.sync` 下发；影响 FR-88/92。参数 K/M/N 等随基线测试调整，无需改 ADR。

## 验证

- PoC（进入 P3 前）：用故障注入验证「单探针单次失败不摘除」「联合条件满足才摘除」「恢复需连续成功」「hold-down」「最小健康下限」；闭环 F（AC-F-1..6）。
- DNS：`dig` 对各记录类型与不同来源线路的应答测试、多 NS 一致性、响应限速测试；缺真实多区域/多 NS 环境则标「等待环境验证」（ADR-023）。
